# 1.4.0 兼容性与匿名统计可诊断性设计

## 背景与目标

`1.4.0-alpha.1` 已完成加固前风险检查和单 APK 操作闭环，并在公开下载和匿名工具使用中获得持续反馈。Issue #109 表明，当前内置 apktool `3.0.1` 无法重打包含 `android:enableOnBackInvokedCallback` 的 Manifest；该问题是工具链兼容缺口，不是 uni-app 不支持加固。

同时，桌面端每日匿名统计请求已经携带随机 `anonymous_id`、`app_version`、平台和架构，但 Worker 的公开查询只按日期聚合，维护者无法按版本查看成功和失败；失败也只有总次数，无法按任务阶段判断异常是否集中。

本阶段目标是在不扩大用户数据采集边界的前提下：

1. 使用新版 apktool 处理 Android 新 Manifest 属性，并以项目自建样本稳定回归；
2. 让 `1.4.0` 起的匿名聚合统计能够按工具版本、任务类型和失败阶段分析；
3. 将统计增强与兼容修复一同在 `1.4.0-alpha.2` 发布，之后 Beta 冻结统计协议和产品功能。

## 范围与非目标

### 本阶段范围

- 将仓库和三平台 GUI 发布包内置 apktool 从 `3.0.1` 升级到 `3.0.3`。
- 为 `android:enableOnBackInvokedCallback` 增加可重复构建的 Manifest 回归样本，并接入现有端到端加固链路。
- 保留现有按日期的匿名统计，新增按版本的聚合查询和失败阶段汇总。
- 在桌面端本地每日汇总中记录固定枚举的失败阶段；上传时仅发送聚合计数。
- 在统计脚本和维护统计快照中保存版本维度与失败阶段维度，缺失字段以“不可用”处理，不用零伪造历史数据。

### 明确非目标

- 不从加固后的 APK 上报数据，不统计最终用户、安装量、包名或应用运行情况。
- 不新增或更换机器标识。现有 `anonymous_id` 是首次生成的随机 UUID，仅用于桌面工具安装实例的日去重；不读取设备序列号、MAC、用户名、硬盘信息或 IP。
- 不上传 APK、路径、原始错误文本、业务包名、证书材料、密码、签名指纹、完整 Android 版本或设备型号。
- 不试图将历史日期重新归属到版本或失败阶段。新查询仅展示数据库已实际保存的版本字段；旧统计快照保持原口径。
- 不改变 DEXB、运行时加载、签名、Root 策略、Android 最低支持版本或 AAB 支持范围。

## 兼容性修复设计

### 工具资源

仓库统一以 `tools/apktool_3.0.3.jar` 作为唯一开发资源。以下位置必须改为引用同一文件：

- Tauri `bundle.resources`；
- CLI、Linux、macOS、Windows 发布脚本；
- 本地工具查找提示和发布检查脚本；
- 端到端回归脚本中的 apktool 解包验证。

发布包内资源名继续保持 `tools/apktool.jar`，不让安装包路径暴露内部版本差异；“关于/诊断”页仍以运行时 `--version` 输出实际版本。

### 自建回归样本

现有 `tests/fixtures/android-smoke-app` 的 `compileSdk` 与 `targetSdk` 已为 35，可在 `<application>` 节点声明：

```xml
android:enableOnBackInvokedCallback="true"
```

端到端脚本应在以下节点验证该属性：

1. 原始 Release APK 能被 apktool `3.0.3` 解包和重打包；
2. 原始 APK 经加固、重签后仍可被 apktool 解包；
3. 加固产物的 Manifest 保留该属性；
4. 现有多 DEX、`extractNativeLibs=false`、Native 库不压缩和 16 KB ZIP 对齐检查继续通过；
5. 有设备时复用既有覆盖安装与两次启动回归。

该夹具只验证开源 Android 标准属性，不包含用户 APK、uni-app 资源或业务数据。若 #109 用户之后提供样本，样本只在本地或经授权的私下渠道验证，仓库仅记录脱敏结论。

## 匿名统计设计

### 已有数据与迁移原则

当前客户端请求已含：`anonymous_id`、`usage_date`、`app_version`、`platform`、`arch` 和六个任务计数。当前 D1 的主键为 `(anonymous_id, usage_date)`，同一工具实例在同日升级并上报时会覆盖旧版本记录；当前 `/stats/trend` 又会丢弃 `app_version`。

`1.4.0-alpha.2` 使用显式的第二代存储表，主键改为 `(anonymous_id, usage_date, app_version)`。迁移时保留旧 `daily_usage` 表供原客户端继续写入和趋势查询；新客户端写入第二代表。Worker 的聚合查询同时读取两张表，但对同一匿名实例、日期、版本只计一次，避免过渡期重复。旧表缺少失败阶段，查询将其纳入总失败次数，不虚构阶段分布。

### 本地数据模型

每日统计由“日期 + 工具版本”索引，而非仅日期。版本采用编译期 `CARGO_PKG_VERSION`，不接受前端输入。

除既有六个计数外，新增固定枚举的失败桶：

| 操作 | 阶段 | 含义 |
|---|---|---|
| `protect` | `prepare` | 工具检查、证书读取、输入预检或任务准备失败 |
| `protect` | `unpack` | apktool 解包失败 |
| `protect` | `manifest` | Manifest 修改或资源重打包失败 |
| `protect` | `dex_runtime` | DEX 处理、资源注入或 Native 库处理失败 |
| `protect` | `align` | 对齐或 Native 库 ZIP 策略复验失败 |
| `protect` | `sign` | 加固任务的后续自动签名失败 |
| `sign` | `prepare` | 独立签名的证书、参数或工具准备失败 |
| `sign` | `align` | 独立签名任务的对齐失败 |
| `sign` | `execute` | apksigner 执行或验签失败 |
| `task` | `cancelled` | 用户主动取消，不作为错误计入失败率 |
| `task` | `unknown` | 无法由任务状态可靠归属的非取消失败 |

阶段从既有任务步骤和结构化执行结果确定，不解析、上传或持久化原始错误文本。加固任务的“加固失败总数”与自动签名失败应分别累计，避免一次失败被当成两个加固失败；取消只进入 `task.cancelled`，不计入 `protect_failed_count` 或 `sign_failed_count`。

### 上传契约

保留 `POST /events/daily`，新客户端附加 `failure_counts`：

```json
{
  "anonymous_id": "随机 UUID",
  "usage_date": "2026-08-25",
  "app_version": "1.4.0-alpha.2",
  "platform": "macos",
  "arch": "aarch64",
  "app_start_count": 2,
  "protect_start_count": 1,
  "protect_success_count": 1,
  "protect_failed_count": 0,
  "sign_success_count": 1,
  "sign_failed_count": 0,
  "failure_counts": [
    { "operation": "protect", "stage": "manifest", "count": 1 }
  ]
}
```

Worker 严格白名单校验操作、阶段和每项计数上限。缺少 `failure_counts` 的旧客户端请求保持兼容。任何未知字段忽略，不写入数据库。请求失败、超时或 Worker 不可用时，桌面端不得影响加固和签名主流程，且未确认上传的数据保留供后续启动重试。

### Worker 查询与维护口径

保留 `GET /stats/trend?days=N` 的既有 `data` 数组，保证项目统计脚本和旧页面兼容。响应新增可选字段：

- `versions`：按 `usage_date + app_version` 汇总的启动、加固、签名和活跃实例数；
- `failure_breakdown`：按 `usage_date + app_version + operation + stage` 汇总的失败计数；
- `schema_version`：用于脚本判断维度是否可用。

`scripts/project_stats.py` 保持原有总量计算，另外保存 `usage.version_trend` 与 `usage.failure_breakdown`；服务端没有返回新字段时标记 `available=false` 的细分维度，不把它写为零。维护页面如恢复展示，只显示“匿名桌面工具使用情况”，不称为被加固应用活跃度或真实用户数。

## 发布与验收

### `1.4.0-alpha.2`

- 新 apktool 通过自建 Manifest 样本、核心单元测试、脚本测试、端到端加固回归和三平台 GUI 打包；
- Worker 迁移在本地 D1 测试和远端预演中验证旧/新客户端写入、重复上报幂等、版本查询与失败桶查询；
- GUI 设置页保留用户可关闭的“匿名使用统计”开关，并更新说明为“仅发送桌面工具的匿名每日聚合计数与固定失败阶段，不上传 APK、路径或错误日志”；
- Release Notes 明确说明这是兼容性与统计可诊断性 Alpha，不把下载量或聚合实例数描述为真实用户数。

### `1.4.0-beta.1` 门槛

- Alpha.2 至少观察一到两周；
- 新版 apktool 未出现可稳定复现的阻塞性解包、重打包、安装或启动问题；
- `failure_breakdown` 未出现某一版本和阶段的持续异常集中；
- 三平台发布产物、版本号、统计隐私说明、回归文档和 Release Notes 全部一致。

Beta 发布后冻结统计契约、工具链版本和产品功能；只修阻塞问题。RC 与正式版不再临时追加统计字段或保护机制。

## 风险与回退

- apktool 升级可能改变资源重打包结果，因此必须以既有端到端样本和真实设备覆盖安装验证；若发现阻塞回归，停止 Alpha.2 发布并保留 `3.0.1` 作为调查基线，不在正式版本中混用两个默认 apktool。
- D1 第二代表和查询逻辑必须在上线前用测试数据库演练。若 Worker 部署失败，桌面端上传失败仅延迟重试，主流程不受影响；公开趋势继续至少返回旧的日期聚合。
- 统计阶段仅是任务流水线分类，不能替代用户日志或证明根因。某桶异常时，先通过 Issue 的脱敏诊断摘要和可授权样本复现，再决定是否修复。
