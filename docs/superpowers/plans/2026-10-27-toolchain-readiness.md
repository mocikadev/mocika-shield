# 工具链就绪检查与维护收尾

## 目标与边界

维护者已确认先完成 1.4.2 发布文档收尾，再审查工具链自检和错误引导，最后以本地证据决定是否进入性能优化。不等待观察期，但不因零散错误计数推定产品缺陷，不自动发布 1.4.3。

本阶段不修改用户 Java 默认环境、真实证书、匿名采集、数据库、壳资源、运行时安全策略或加固格式；不恢复 Computer Use，不新增常驻面板、环境配置字段或日常重型 CI。保留自动签名的证书指纹核对，不能以减少依赖为由绕过签名绑定。

## 审查结论与架构

- 关于页和实际执行均复用共享核心的 Java/keytool 定位规则，PATH 优先、JAVA_HOME 兜底和关联 JDK 的修复仍有效，不重新实现探测。
- 关于页已有刷新环境与复制脱敏诊断入口，不新增重复入口。
- 前端 `getProtectJavaError`、`getSignJavaError` 无条件要求 keytool，但纯加固与使用已保存证书独立签名的执行链只需要 Java；加固后自动签名仍会用 keytool 核对证书，必须保持要求。
- `read_java_version` 未验证子进程退出状态；版本无法读取又统一提示“版本过低”，需要区分未知状态与明确低版本。
- 线上 `TOOL_NOT_FOUND`、`TOOL_PROCESS_FAILED` 只说明类别，以上代码缺口不等于已证明是用户这几次失败的根因。

架构判断为 L2：前端任务依赖判定与核心版本就绪检查的局部协同，不增加业务能力、模块、外部依赖、共享状态或公开协议。核心保留 Java 探测职责，前端既有 `lib/java.ts` 仅映射当前任务所需条件和双语提示，工作流传入已冻结前的自动签名意图。测试分别验证纯函数、隔离子进程和真实 JDK，不依赖 GUI、网络或用户数据库。

## 性能专项准入

先检查已有测量与当前可用样本，再决定是否需要新增采样工具。只在维护者本地离线运行；不上传 APK、路径、阶段耗时或日志，不新增桌面遥测。

测量需区分预检/证书读取、解包、DEX、壳注入、重建、对齐和签名，同时记录输入规模、Java 调用次数、临时目录占用与样本条件。小型自建夹具只能验证测量入口，不能据此判定真实大 APK 的瓶颈或宣称跨设备加速。若原有真实大 APK 不在本机，保留待样本的测量项，不擅自下载业务 APK、不以无关用户附件替代。

只有可复现瓶颈及足够收益证据同时成立，才另行设计局部优化；保留 apktool/apksigner、16 KB 对齐、签名绑定、双资源和旧流程回退。不在本阶段实施 ZIP/Manifest 重写、JRE 内置、AAB 或内存 DEX。

## 性能测量入口的本机试跑

当前 Downloads 未找到原有真实大 APK；未解压或使用无关附件，也不自动重新下载业务样本。仅复用上轮自建的 669,138 字节双 DEX APK，在默认本机 Java 环境下进行两次纯加固，用既有 CLI JSON 进度事件的接收时间分段，200 毫秒间隔抽样 `du -sk` 统计隔离 TMPDIR。这里是测量方法试跑，不是性能优化前后对照，也没有测得真正临时空间峰值或实际 Java 子进程数。

| 项目 | 第一次 | 第二次 |
|------|-------:|-------:|
| 总耗时 | 3,864 ms | 3,402 ms |
| 首次进度之前 | 455 ms | 36 ms |
| 检查阶段（含签名预检） | 403 ms | 390 ms |
| 解包 | 1,948 ms | 1,920 ms |
| DEX 处理 | 352 ms | 353 ms |
| 壳注入 | 15 ms | 16 ms |
| 重建 | 658 ms | 655 ms |
| 对齐与产物检查 | 33 ms | 32 ms |
| 临时目录抽样最大值 | 5,004 KiB | 5,000 KiB |

两次均成功、原始输入哈希未改变。Manifest 阶段在毫秒取整下为零，不表示完全无成本。对齐阶段包括末尾检查与临时目录清理；进程启动、预检和抽样自身也有开销，不把这些数据当成函数级精确性能。加密随机性造成两次输出体积略有差异属于预期。

隔离 keytool 的 Java 8 功能回归另耗时约 5,060 ms（加固）、412 ms（独立签名），环境不同，不与上述两次计算“变慢/加速”。测试文件均在本轮 `/tmp/mocika-toolchain-audit.7USGwi`，不进入仓库或 Release，不产生 GUI 遥测。
