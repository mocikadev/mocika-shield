## 下一版本：`1.4.0` 可靠性与使用效率

### 版本目标

重组“选择 APK—评估风险—确认方案—执行—查看结果”的加固体验：让用户在加固前看到明确风险，复用持久化默认方案，方便修改输出文件名，并形成可安全分享的单 APK 诊断闭环。

本版本不改变 DEXB v5、运行时加载路径、缓存协议、Root 默认策略和 Android 最低版本承诺。

### 计划范围

| 阶段 | 能力 | 完成标准 |
|------|------|----------|
| `1.4.0-alpha.1` | 加固页重组、持久化方案与核心预检 | 完成任务摘要、设置抽屉、文件名/目录分离和默认方案持久化；`shield-core` 输出稳定检查项、风险等级与错误分类，GUI 展示“可继续 / 有风险 / 必须阻止” |
| `1.4.0-alpha.2` | 脱敏诊断与回归校准 | 生成不含路径、证书、密码、包名、业务类名和原始错误文本的单次任务摘要；使用真实问题样本校准预检和错误提示 |
| `1.4.0-beta.1` | 真实 APK 与三平台回归 | Issue 与 QQ 群已有样本完成回归；Linux、macOS、Windows 展示和路径语义一致；风险提示不会把已支持场景误判为阻断 |
| `1.4.0-rc.1` | 功能冻结与发布审计 | 只修阻塞缺陷；版本号、文档、三平台 GUI 产物和正式包内容通过发布前检查 |
| `1.4.0` | 稳定发布 | RC 产物达到正式发布门槛，不临时追加功能 |

### 首轮预检项

- 已完成：`minSdkVersion`、`targetSdkVersion`、`extractNativeLibs` 三态、`org.apache.http.legacy` 信号，以及通过 Manifest `split` 属性识别单独选择的 split APK。
- DEX 数量、总体积、单 DEX 大小和是否已经包含 Mocika Shield 载荷。
- APK 签名状态、签名方案和可读取的证书摘要；不输出证书密码。
- Native ABI 集合、SO 压缩方式、16 KB ZIP/ELF 基础条件。
- Android 4.4 工控兼容模式的 ABI 与 Native 库限制。
- ARouter、`org.apache.http.legacy` 等已有兼容处理所需的可识别信号。
- 疑似其他加固壳、动态加载框架或异常 APK 结构；只给出风险说明，不声称能够准确识别所有厂商壳。

### 风险等级

| 等级 | 行为 |
|------|------|
| 可继续 | 输入满足当前正式能力，正常进入加固 |
| 有风险 | 允许用户确认后继续，报告中说明可能影响的系统或功能 |
| 必须阻止 | 已加固、未签名、签名计划不一致、资源能力不支持或确定会生成不可安装/不可启动产物 |

### 明确非目标

- 不增加在线 APK 上传、云端分析或远程证书处理。
- 不把完整 APK 路径、密码、用户目录、业务包名或证书材料写入匿名统计。
- 批量加固暂缓，不作为 `1.4.0` 的范围或后续阶段的前置条件；未来如恢复评估，必须复用单 APK 的预检与任务快照。
- 不把 CLI 作为正式 Release 产物，也不增加单独的 CLI CI 打包任务。
- 不借预检改造 APK 重写、签名、运行时加载或加密协议。

## 后续候选

候选方向不等于已排期版本；只有需求、依赖条件和验收资源同时具备后才进入“下一版本”。

| 方向 | 当前状态 | 进入条件 |
|------|----------|----------|
| AAB 正式支持 | 条件受阻 | 已完成单 base 模块可行性实验；需要 Google Play 账号、Play 应用签名和内部测试轨道完成真实闭环，详见 [AAB 可行性结论](../design/aab-feasibility.md) |
| 工具链局部轻量化 | 待专项原型 | 先用数据证明 apktool 或整包重建是主要瓶颈；未知结构必须保留可靠回退，详见 [工具链研究](../design/toolchain-modernization.md) |
| 可选资源保护 | 需求驱动 | 有真实用户场景、资源选择和应用侧读取接口设计；不通过 Hook 透明拦截，详见 [资源保护研究](../design/asset-protection.md) |
| 供应链成熟度 | 持续评估 | 具备代码签名、公证或发布证明所需账号、证书与维护成本 |

## 已暂停或停止的方向

| 方向 | 状态 | 结论 |
|------|------|------|
| API 29 以上完整内存 DEX | 暂停产品接入 | 公开加载链路和回退状态已完成大量实验，但真实大 APK 的长期内存性价比门禁未通过；不再占用 `1.4.0` 版本号，详见 [内存 DEX 设计](../design/memory-dex-production.md) |
| DEX 结构与方法代码分离 | 停止产品接入 | 离线协议、真实多 DEX 和攻击测试已完成；公开运行时仍要求形成完整 DEX，继续只能依赖高风险私有运行时或独立虚拟机，详见 [代码分离研究](../design/dex-code-separation.md) |
| ART/系统函数 Hook、自修改代码、可写可执行内存 | 禁止 | 与多版本兼容、安全软件风险和项目安全边界冲突，不进入正式方案 |
| 独立在线加固服务 | 不计划 | 项目保持本地离线处理，不托管用户 APK、证书或密码 |

## 并行维护规则

- `main` 始终保持可发布；复杂功能使用临时 `feat/*` 或 `fix/*` 分支，合并后删除。
- 稳定版 Issue 和 QQ 群反馈持续观察，但只有可复现高优先级缺陷才抢占当前开发任务。
- 一个小版本聚焦一个主题；预检、运行时安全、AAB 和工具链重写不得混成一次发布。
- Alpha 可以完成计划内能力；Beta 起冻结功能与协议；RC 只修阻塞正式发布的问题。
- 每个阶段形成完整代码、测试和文档后再提交，不因细小修改堆积多个 PR。
- 已完成内容不再复制回本文件；版本结果进入 Release Notes 或[路线图历史档案](roadmap-history.md)，实验数据进入对应设计文档。

## 下一步执行顺序

1. 先重组加固页信息结构，定义设置抽屉、持久化默认方案、输出文件名与目录规则以及任务状态切换。
2. 盘点现有 `check_apk`、Manifest、ABI、签名和 Native 对齐检查，定义统一预检结果模型。
3. 在 `shield-core` 实现只读扫描、风险分级和单元测试，再把结果接入新的加固页布局。
4. 单 APK 配置、预检和执行形成完整闭环后发布 `1.4.0-alpha.1`；随后完成脱敏报告和真实样本回归校准，不因单个检查项单独发布版本。
