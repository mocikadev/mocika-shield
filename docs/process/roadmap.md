## 当前维护：工控混合架构单包兼容

用户需要一包覆盖 4.4 ARM 工控板和较新设备，允许排除第三方附带的 `armeabi`。[混合架构方案与任务](../design/android-4.4-mixed-abi.md)已完成本地实现、自动化与 rc.3 三平台发布，并收到该版在 Android 4.4／6.0／10.0／11.0 上测试正常的用户反馈，按该用户使用场景验收通过。不取消完整性检查、不新增布局、不扩张真正旧 ARM、4.4 x86 或未经验证的厂商硬件；不反复要求用户重测。

## 后续维护方案：壳类名与 JNI 绑定

已按[壳类名去品牌化方案](../design/stub-identity.md)完成首期实现并合并 PR #137：消除 `dev.mocika.shield.loader.Ld` 残留，完整保留 JNI 回调成员，全部 Native 注册和签名回调使用同批 R8 名称及签名映射；补充资源契约审计和业务类名冲突检查。标准／工控资源构建、双 DEX 加固签名、本机 JVM 注册及 macOS `.app` 校验通过；一加 8／API 37 真机上，标准／工控资源各自的 ARM64、ARMv7 启动、旧壳覆盖升级、缓存复用及工控 ARMv7 热缓存下的 Root 拒绝已通过。后续 Windows 资源与 16 KB ARM64 补验已通过，当前新壳的低版本及 x86 设备运行仍未复测。不改 UI、配置、DEXB 或加载策略，暂不实现每任务全命名空间随机化；随 rc.4 交付，不改已公开 rc.3，也不追加 1.4.2 正式发布的新阻塞项。

## 当前维护：Native 暴露面检查

按[Native 暴露面方案](../design/native-surface.md)完成构建期检查并合并 PR #138：仅允许 `JNI_OnLoad` 导出，禁止普通符号表、调试内容、原始桥接路径与已列明的构建机用户路径。修复工控 v7a 的依赖源码绝对路径残留，统一中文／空格路径参数处理；不修改运行代码或引入混淆加载。44 项脚本测试、三套资源审计、JNI 探针、加固签名、ARM64 与工控 ARMv7 真机运行及 macOS `.app` 校验通过。Windows 标准／工控资源手动专项补验已通过；Linux 原生和其他设备矩阵仍待验，不新增版本或日常重型 CI。

## 当前维护：Manifest 运行字段治理

维护者已确认并完成[中性字段与资源协议方案](../design/manifest-runtime-contract.md)，PR #139 已合并：以单一字段定义联动核心写入、Java 读取及产物审计，新核心兼容旧协议资源，旧核心明确拒绝新资源。保持 DEXB、缓存身份与目录、GUI 和加载策略不变，不双写旧品牌字段。核心、Java、脚本、JNI 和完整 `.app` 校验通过；标准／工控各自的 ARM64、ARMv7 旧壳覆盖、缓存复用及工控热缓存严格 Root 拒绝已通过，新协议 Windows 资源和 16 KB ARM64 专项另行验证通过。该改动不新增系统版本依赖，当前主线 Android 4.4 未重新实测如实保留，但不追加整套系统复测或旧模拟器恢复前置条件；随 rc.4 交付，不改已公开 rc.3。

## 暂缓跟进：中文工具链输出编码

QQ群反馈中文 APK 文件名加固时报错乱码及签名识别失败。已复现并修复 Java 非 UTF-8 输出按 UTF-8 读取的缺陷，统一共享核心与 GUI 工具探测入口，未改动壳、配置、数据库或加固协议。JDK 8/11/17 编码回归及真实 343 MB 中文名 APK 加固、中文证书签名通过；原生 Windows 与用户签名识别失败是否同源仍待验证。按维护者授权发布 `1.4.2-rc.1` 供受影响用户测试，详见[中文工具链兼容与审计](../design/chinese-toolchain-compatibility.md)。

2026-10-15 维护者说明用户仍有问题，已让用户在其本机源码环境排查；此项暂缓，不将现有编码回归解释为该用户场景已全部修复，不因等待反馈持续增加候选版本。

## 后续候选

候选方向不等于已排期版本；只有需求、依赖条件和验收资源同时具备后才进入“下一版本”。

| 方向 | 当前状态 | 进入条件 |
|------|----------|----------|
| 发布供应链完善 | 可先做基础项 | 优先补充产物来源证明、依赖清单和发布可追溯记录；安装包代码签名与 macOS 公证仍需要账号、证书及持续维护投入 |
| AAB 正式支持 | 条件受阻 | 已完成单 base 模块可行性实验；需要 Google Play 账号、Play 应用签名和内部测试轨道完成真实闭环，详见 [AAB 可行性结论](../design/aab-feasibility.md) |
| 工具链局部轻量化 | 待专项原型 | 先用数据证明 apktool 或整包重建是主要瓶颈；未知结构必须保留可靠回退，详见 [工具链研究](../design/toolchain-modernization.md) |
| 可选资源保护 | 需求驱动 | 有真实用户场景、资源选择和应用侧读取接口设计；不通过 Hook 透明拦截，详见 [资源保护研究](../design/asset-protection.md) |

## 已暂停或停止的方向

| 方向 | 状态 | 结论 |
|------|------|------|
| API 29 以上完整内存 DEX | 暂停产品接入 | 公开加载链路和回退状态已完成大量实验，但真实大 APK 的长期内存性价比门禁未通过；不再占用 `1.4.0` 版本号，详见 [内存 DEX 设计](../design/memory-dex-production.md) |
| DEX 结构与方法代码分离 | 停止产品接入 | 离线协议、真实多 DEX 和攻击测试已完成；公开运行时仍要求形成完整 DEX，继续只能依赖高风险私有运行时或独立虚拟机，详见 [代码分离研究](../design/dex-code-separation.md) |
| ART/系统函数 Hook、自修改代码、可写可执行内存 | 禁止 | 与多版本兼容、安全软件风险和项目安全边界冲突，不进入正式方案 |
| 独立在线加固服务 | 不计划 | 项目保持本地离线处理，不托管用户 APK、证书或密码 |

## 并行维护规则

- `main` 始终保持可发布；复杂功能使用临时 `feat/*` 或 `fix/*` 分支，合并后删除。
- 稳定版 Issue 和 QQ 群反馈持续观察，但只有可复现高优先级缺陷才抢占当前开发任务。
- 一个小版本聚焦一个主题；预检、运行时安全、AAB 和工具链重写不得混成一次发布。
- Alpha 可以完成计划内能力；Beta 起冻结功能与协议；RC 只修阻塞正式发布的问题。
- 每个阶段形成完整代码、测试和文档后再提交，不因细小修改堆积多个 PR。
- 保持本地离线定位，不新增 APK 联网、云端 APK／证书处理、原始日志上传或 CLI 发布包；批量加固继续暂缓。
- 已完成内容不再复制回本文件；版本结果进入 Release Notes 或[路线图历史档案](roadmap-history.md)，实验数据进入对应设计文档。
