# 失败分类与用户确认错误报告方案

> 状态：1.4.0-beta.5 本地实现、自动化验收与代码复审完成，已提供 macOS 测试应用。2026-09-16。人工界面、Windows/Linux 原生及线上验收待进行；尚未提交、迁移、启用接口或发布。

## 目标与范围

减少只能等待少数用户反馈的盲区：自动判断失败主要集中在哪个软件版本、操作阶段和错误类别；用户同意后补充一次失败的安全诊断证据。只发生在 Mocika Shield 桌面 GUI，绝不向加固后的 APK 增加上报、联网或最终用户识别能力。首期覆盖加固、独立签名和证书识别/校验/创建失败，不收集业务内容，不建设新的公开看板。

Beta.4 基线提供随机匿名实例标识、按日期和工具版本累计的启动/加固/签名计数与失败阶段，不含错误报告。当时 `main.rs` 主要在失败结果转为字符串后记录阶段，原始错误类型、退出码等证据容易丢失；Beta.5 在转换字符串前提取受控诊断，不以界面错误字符串作为网络载荷。

## 方案比较与决定

| 方案 | 收益 | 问题 | 决定 |
|------|------|------|------|
| 只增加匿名错误码 | 自动覆盖面大、敏感信息少 | 未知错误细节不足 | 必做的基础层 |
| 匿名错误码 + 每次经确认发送安全报告 | 自动发现趋势，同时获得版本和环境证据 | 需要单独的预览、发送和存储边界 | 推荐方案 |
| 默认自动上传完整日志或依靠正则脱敏全文 | 能看到更多原始上下文 | 可能泄露密码、路径、业务内容，扩大已有统计承诺 | 不采用 |

架构按 L3 审视：增加跨客户端/服务端协议及受限报告存储。在当前仓库内实现；不引入 Bugly、不嵌入管理密钥、不增加数据库产品。维护者已明确授权 Beta.5 实施，不修改 Beta.4 发布产物。

## 两条独立通道

| 项目 | 匿名统计 | 错误报告 |
|------|----------|----------|
| 触发 | 操作失败后累计固定类别 | 用户在失败弹窗中确认发送 |
| 控制 | 现有 `telemetry.enabled`，默认行为不变 | 每份报告单独确认，没有默认自动发送开关 |
| 标识 | 沿用随机匿名安装实例 UUID | 每份报告随机 UUID，不带匿名统计 UUID、机器标识或任务路径 |
| 数据 | 日期、软件版本、操作、阶段、错误码及次数 | 版本、受控环境字段、错误码、退出码和白名单证据 |
| 接收 | 现有 Worker `/events/daily` 可选扩展 | 同一 Worker 新建 `/reports/errors` |
| 存储 | 现有 D1 增加错误类别聚合表 | 同一 D1 独立 `error_reports` 表，不混入使用次数 |
| 查询 | 按版本/日期聚合，兼容旧趋势 | 仅维护者认证访问，不接入公开趋势或 `stats` 分支 |

关闭匿名统计，不妨碍用户主动发送当前报告；弹窗明确“本次发送不会开启匿名统计”。反之，允许匿名统计不等于自动允许报告发送。拒绝报告不影响原有统计开关和加固/签名功能。

## 版本关联：失败发生时冻结，不按上传时间归属

首期必须区分以下字段，不只记一个含糊的“版本”：

| 字段 | 来源与意义 |
|------|------------|
| `app_version` | 后端编译版本，例如 `1.4.0-beta.4`；发生失败时冻结，不能由前端自由填写 |
| `schema_version` | 上传协议版本，与应用版本分离 |
| `classifier_version` | 固定错误分类规则版本，便于规则改变后的解释与对比 |
| `sanitizer_version` | 单次报告白名单/脱敏规则版本，不用于匿名计数 |
| `build_revision` | 发布构建的源码提交短哈希；构建时可用则写入，取不到为 `null`，不得查询/上传用户工作目录 |
| `build_kind` | 固定枚举 `release` / `local` / `unknown`，不是任意渠道字符串 |
| `java_major`、`java_vendor` | 仅报告包含；数字主版本与固定厂商枚举，不传含路径的完整 `java -version` 文本 |
| `tool_name`、`tool_version` | 仅报告包含；工具名枚举及安全解析后的版本号，无法解析为 `null` |

版本号必须保留完整预发布后缀；`1.4.0-beta.3`、`1.4.0-beta.4`、`1.4.0` 分开统计，不能按字符串字典序判断版本先后。缺失字段明确为空或不可用，不能假定历史客户端使用当前规则。

匿名失败按 UTC 日期归属。报告用客户端 `occurred_at` 和服务端 `received_at` 分别保存发生时间、接收时间；客户端时钟不可信，限流和保留期限均以服务端时间为准。客户端升级、重试或重开弹窗不得把旧任务改归新版本。首期报告不跨进程排队，关闭应用后没有报告后台续传。

`app_version` 和报告内容仍属于客户端声明，不能作为可信证明；公开桌面客户端无法靠内置静态密钥防止伪造。

## 错误分类与计数口径

新增 `FailureCode` 稳定枚举。分类优先使用核心类型错误和子进程结构化结果，其次使用按工具限定、可测试的特征匹配。不得按“日志中出现了某个词”跨工具猜测；不确定返回 `UNKNOWN`，不把原始文本或其哈希作为类别。

初始类别：

| 错误码 | 可确认的含义 | 是否主动弹反馈框 |
|--------|------------|------------------|
| `TOOL_NOT_FOUND` / `JAVA_UNSUPPORTED` | 必需工具缺失 / Java 不满足要求 | 否，提供明确修正提示 |
| `FILE_NOT_FOUND` / `PERMISSION_DENIED` / `DISK_FULL` | 明确的文件/权限/空间错误 | 否，保留手动反馈入口 |
| `UNSUPPORTED_ABI` | 已确认的不支持 ABI 导致失败 | 否，优先展示排除/重新打包建议 |
| `KEYSTORE_PASSWORD_INVALID` / `KEY_ALIAS_NOT_FOUND` | 明确口令或 Alias 校验失败 | 否，优先引导修正 |
| `KEYSTORE_FORMAT_INVALID` | 明确不匹配/无效的证书格式 | 否，保留手动反馈入口 |
| `TOOL_OUTPUT_ENCODING_INVALID` | 输出字节不满足约定编码 | 是 |
| `MANIFEST_REBUILD_FAILED` / `APK_REPACK_FAILED` | 指定工具/操作的回编或重打包失败 | 是；是错误类别，不冒充根因 |
| `RUNTIME_INJECTION_FAILED` / `ALIGNMENT_FAILED` / `SIGNING_FAILED` | 对应步骤失败但未能进一步细分 | 是 |
| `TOOL_PROCESS_FAILED` / `UNKNOWN` | 子进程异常 / 无法可靠分类 | 是 |

取消任务不是失败，不弹反馈框，也不计入失败类别。预检阻止、空字段校验不增加“执行失败”次数；证书操作若实际调用后端并失败，可在新的 `certificate` 操作维度记录，不修改加固/签名次数。证书密码等输入问题虽然不主动弹窗，仍可作为实际操作失败的固定类别累计；不得记录输入内容。

一次任务终态只能记录一次失败。加固完成后的自动签名失败保留“加固成功 + 自动签名失败”的业务事实，不能将整个流程再记一次加固失败；用 `flow=protect_with_sign`、`operation=sign` 区分其来源。进度事件、异常返回、页面重挂载不得重复累计。同一任务仅一个主错误码，其他安全证据只属于报告。

阶段与原因是不同维度：沿用现有 `failure_counts` 阶段计数，新增可选 `failure_reason_counts`，单项为 `flow/operation/stage/code/classifier_version/count`。原因总数不能与阶段总数相加；报告发送次数也不能再计作失败次数。类别是程序可确认的解释，不承诺所有类别都是最终根因。

## 报告内容与脱敏边界

首期不是“上传完整日志”，而是由后端生成的有限诊断报告：

- 必填：报告 UUID、协议/分类/脱敏规则版本、应用版本、发生时间、操作/阶段/主错误码。
- 可选：系统家族、系统版本号、CPU 架构、Java 主版本/厂商、内置工具名/版本、退出码、固定运行模式枚举及白名单证据。
- 系统版本通过结构化接口获取并验证格式；Linux 发行版只接受固定名称集合和版本号，不上传完整 `/etc/os-release`。可选字段获取失败不阻止用户工作。
- 证据以固定模板 ID + 白名单参数表达。例如“keytool 输出不是有效 UTF-8”“apksigner 非零退出，退出码 1”；可包含固定允许集合内的标准异常类型、支持的 ABI 枚举。不能把异常对象、调用栈、JSON 任意扩展字段或错误字符串直接序列化。
- 后端先白名单提取，再做已知敏感值检查；发现疑似路径、密码、证书别名、包名、URL 或高熵未知文本时舍弃该条。正则只作第二道检查，不能作为完整日志的通行证。
- 首期不提供自由文本输入和附件。未知错误仍可报告受控环境、阶段和退出码，但提示“无法安全提取更多错误细节”；维护者可能仍需用户另行提供脱敏日志，不能承诺本机制覆盖所有问题。

永不包含 APK/证书文件、证书密码、Alias、DN、指纹、包名、业务类名、路径、用户名、机器名、环境变量、完整命令行、网络凭证或整个任务日志。也不发送这些值的哈希。Java/工具版本号长度和字符集受限，无法解析不透传原文。

报告 JSON 总大小不超过 8 KiB，证据不超过 10 条，单条模板渲染文本不超过 256 字符；先选择/舍弃字段，再验证最终 JSON，不能截断 UTF-8 字节造成坏数据。客户端与服务端都验证；服务端拒绝额外字段和任意日志正文。

## 弹窗与发送状态

任务失败页面继续保留原错误及重试入口，符合规则时仅弹一次：

> 操作失败，是否发送错误报告？
>
> 报告包含软件和运行环境版本、失败阶段及经过筛选的错误摘要，用于帮助定位问题。不会上传 APK、证书文件、密码或完整日志。
>
> 查看报告 / 暂不发送 / 发送报告

“查看报告”显示后端生成的实际载荷和中文字段解释，注明发送至项目 Cloudflare 服务、报告保存 30 天。全部待发送字段可查看，不能在确认后偷偷补字段。未开启统计时展示独立发送说明。错误报告窗口不能遮断原始错误详情；关闭窗口等同暂不发送。

同一次任务只提示一次；同一应用会话中，相同 `flow/operation/stage/code/app_version` 拒绝或发送后不再主动提示，错误页仍可手动打开。重新打开不会生成重复失败事件。第一版不增加“永远自动发送”选项，避免与现有统计开关混淆。

状态为：本地待确认 → 查看/拒绝 → 用户发送中 → 已发送或发送失败。拒绝不联网；关闭应用不后台发送；发送中不允许重复点击。用户确认启动请求后，关闭弹窗不代表撤回已经提交的数据，文案需明确。发送成功展示报告编号，用户可在 QQ 群或 issue 中引用，不自动发 issue。

后端缓存最多 5 份待确认的安全快照，最多保留当前进程内 30 分钟；过期明确提示重新操作。前端只提交报告 ID 和预览摘要校验值，后端验证属于当前任务的不可变快照，不接收任意日志内容。确认后发送的内容必须与预览完全一致。网络超时 10 秒、首期不自动重试；用户可手动重试同一报告 ID，发送结果不影响加固重试或证书保存。

## D1 存储、接口与维护查询

继续使用现有 Worker 与 D1，不增加对象存储：8 KiB 以下的结构化报告无需文件桶。完整日志不上传，原有本地错误展示/诊断行为不变，也不为本方案新增原始日志持久化。

### 匿名错误类别表

新增 `daily_usage_failure_reason`：主键包含 `anonymous_id/usage_date/app_version/flow/operation/stage/code/classifier_version`，值为累计 `count`。采用累计快照而非追加事件；同一键重复上传不翻倍，乱序时保留较大累计值。客户端同日计数只增不减。默认现有开关控制，不新增新的匿名身份。

旧表和旧 `failure_counts` 保留。请求不带新字段时不创建原因数据，也不得清空先前已收到的原因数据。新增趋势字段 `failure_reason_breakdown` 和能力/覆盖标识；缺失历史分类是“不可用”，不填成 `UNKNOWN` 或零。针对开启新能力客户端，维护查询显示已分类、UNKNOWN 及未提供分类的覆盖差异。

### 单次报告表

新增 `error_reports`：`report_id` 主键；`schema_version/app_version/build_revision/build_kind/classifier_version/sanitizer_version/occurred_at/received_at/flow/operation/stage/code/platform` 可索引/查询，余下受控字段存 JSON。建立 `(app_version, received_at)` 与 `(code, received_at)` 索引，不存匿名统计 UUID，不凭 IP 关联报告与统计。

接口 `POST /reports/errors`：只接受指定 JSON schema；首次写入返回 201 和报告编号；相同 ID、相同规范化载荷重试返回 200；相同 ID 但不同载荷返回 409，不能覆盖旧报告。校验失败 400，超大 413，限流 429，临时存储失败 503。服务端生成的接收时间不参与客户端幂等摘要。

报告不新增公开读取接口；维护者初期通过已配置授权的 D1 CLI/API 参数化查询，不建设管理网页，不在桌面端内置读取令牌。报告编号不是访问凭证。后续如增加管理接口，必须单独认证授权、禁用公共缓存并记录访问审计。输出报告时视为不可信数据，仅作纯文本展示，不执行其中内容。

维护查询默认按完整应用版本和日期过滤，提供：失败类别排行榜、UNKNOWN 占比、阶段分布、对应版本报告数量及平台/Java 主版本分布。报告是主动反馈的样本，不可代替全体失败率；没有匿名 UUID，就不宣称报告来自多少独立用户。现有活跃数据有实例跨版本口径限制，本方案不顺便调整该统计。

### 安全、滥用与保留

- HTTPS 上传；部署平台会接触请求 IP 等连接信息，不能声称网络层完全不可识别。应用业务表和报告日志不持久化原始 IP、User-Agent 或请求正文，不记录密码和被丢弃文本。
- 公共上传不能依靠客户端静态 token 或 CORS 当成身份认证。服务端提供总开关、大小/字段限额和限流；日志只记录请求 ID、状态码和计数。
- 初始建议阈值：客户端同一会话最多主动发送 5 份；服务端按来源短期限流 10 次/分钟，并设全局每日最多 1,000 份。数值是项目保护阈值，不是 Cloudflare 套餐额度，部署前验证所用限流设施可用，否则报告入口保持关闭。
- 如用 D1 实现来源限流，只存服务端密钥派生的按日轮换 HMAC 桶和计数，独立表 24 小时清理，不存原始 IP，不将桶写进报告。无法完成原子限额扣减时拒绝接收，不能无上限落库。
- 报告以 `received_at` 保存 30 天，定时清理过期报告并验证清理成功。原有匿名聚合保留策略不因此缩短。报告的主库删除不等于云平台备份立即消失，运维说明须区分主库与平台恢复窗口。
- 独立服务端开关只关闭错误报告入口，不影响现有匿名统计；服务不可达时界面提示失败，不改用户网络配置、不自动转发其他服务、不影响本地工作。

## 模块分工与兼容策略

- `crates/shield-core/src/error.rs` 及工具调用边界：保留类型化错误与受控退出信息；新增错误分类模块，不把前端文本国际化字符串当成错误协议。现有错误显示保留，分类信息在转换成字符串前提取。
- GUI 新建 `failure_diagnostic.rs`：将核心错误与任务上下文转换为冻结快照；新增 `error_report.rs` 管理预览快照、用户发送与独立网络状态。`main.rs` 只注册命令和调用服务，不再扩张业务逻辑。
- `telemetry.rs`：只累计固定错误分类；不保存报告、原始日志或任意错误字符串。`app_config.rs` 新增可选原因计数字段，使用默认值兼容旧 `config.toml`；不更改 `shield.db` 证书结构。
- GUI 加固/签名工作流与证书操作界面接收受控诊断引用，复用一个错误报告弹窗。前端不能把 `String(err)` 直接交给上传接口。证书输入校验不反复弹反馈。
- Worker 新建独立错误码校验与报告接收模块，入口只路由；不能将新逻辑继续堆在 `index.js`。按增量 SQL migration 新建表，不删除历史数据。
- 迁移顺序：先加表与向后兼容服务端 → 验证旧客户端 → 发布客户端 → 开启报告入口。客户端字段未知时明确不可用，不假装上传成功。回滚报告模块保留旧统计功能，旧客户端重发不会擦除新分类。
- 报告详情及其备份不写入 GitHub 公共仓库、`stats/data/history.json`、Release 附件或公开缓存；维护统计脚本只扩展聚合错误码，不抓取报告正文。

## 实施阶段与版本安排

不修改已经发布/正在构建的 Beta.4，不移动其标签。维护者已指定在 **1.4.0-beta.5** 完成此阶段；不另开 1.4.1 候选。可以立即开发，不把线上观察一周或正式版发布作为开发前置条件；不为每个小阶段单独发版本。服务端部署、启用与版本发布另行验收。

1. **分类基础与单元验证**：定义有限错误码、现有错误到类型的映射、任务单次计数和快照冻结；先覆盖 ABI、编码、证书、回编、签名常见故障。加入配置兼容和错误分类测试，确保不改变原错误展示。
2. **匿名原因统计闭环**：增量迁移 D1、兼容请求与查询、客户端累计和重试，维护统计脚本能按版本读取分类。先完成服务端部署验证，再放出客户端字段。
3. **报告闭环**：不可变安全快照、预览弹窗、显式发送、幂等写入、限流、30 天清理和维护者受限查询。全链路功能完成但保持服务端开关关闭，验收通过再启用。
4. **验收与一次阶段交付**：完成 Windows/macOS/Linux 相关路径与编码样本、隐私测试、离线/关闭统计/升级/重试测试，更新设置说明、统计说明和发布说明。整个阶段形成一份 PR 或少量独立可验收 PR，不碎片化提交，不自动创建用户 issue。

## 验收清单

首期落实边界：安全报告仅使用固定错误码、流程阶段、可用退出码和版本/平台字段。`evidence` 固定空数组，Java 版本/厂商及工具版本尚未可靠取得时为 null；`build_kind` 未建立可靠发布注入时为 unknown。不是上传完整日志，也不声称目前已采集这些可选字段。拓展白名单证据时需同步协议版本和隐私测试。部署步骤见[运维手册](../ops/failure-diagnostics.md)，本地验收记录见[实施计划](../superpowers/plans/2026-09-16-failure-diagnostics.md)。

- [ ] 同一 task 的进度事件、异常、页面重挂载与重试发送不重复记失败；自动签名失败不抹掉加固成功。
- [ ] 关闭统计后不自动发送分类；仍可主动发单份报告，且不会开启统计；拒绝弹窗不产生报告请求。
- [ ] 错误发生在旧版本，延迟统计上传后仍归原版本；预览后字段不变，不能从前端伪造任意上传正文。
- [ ] Java 8/17 的中文/GBK、Windows/UNC/Unix 路径、命令行密码、证书 Alias/指纹、包名、URL token、异常栈、无效 UTF-8 和超长输出均通过敏感信息不外发测试。
- [ ] UNKNOWN 不透传原文；报告预览与实际发送规范化载荷一致；可选环境解析失败只留空。
- [ ] 同 ID 重试幂等，不同载荷冲突拒绝；超时后服务端已接收时重试仍返回同一编号；超大、畸形与含未知字段请求被拒绝。
- [ ] 旧客户端缺少原因字段不删新数据；乱序累计不回退、不翻倍；旧历史显示分类不可用。
- [ ] 报告接收、维护读取、日志、公共缓存与 stats 分支隔离；关闭入口、达到限额和网络异常不影响本地任务。
- [ ] 30 天主库过期清理、24 小时限流桶清理和迁移/回滚演练通过；对云备份保留边界有明确运维说明。
- [ ] 版本维度查询能够区分 Beta.4、后续测试版和正式版，报告数量不当作独立用户数或失败总数。

本设计不会消除所有盲区：网络不通、关闭统计、拒绝报告、未知错误无法安全提取时仍缺信息。目标是提高定位证据覆盖率，而不是以“匿名”为由收集完整日志。
