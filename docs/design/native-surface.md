# Native 暴露面审计与构建守门

## 范围与结论

本阶段沿用 `JNI_OnLoad` 加 `RegisterNatives` 的公开接口，只治理构建产物的意外导出、调试符号和构建机路径泄漏。不改 JNI 方法、Java／Native 调用顺序、DEXB、缓存、安全策略、ABI 或 GUI；不增加运行时字符串加密、控制流混淆、私有 ART 接口或自定义 ELF 加载。

检查对象仅为工具自带资源中的壳库，不扩展扫描用户 APK 的业务 Native 库，也不新增任何上报。

动态注册加最小导出符合 [Android JNI 建议](https://developer.android.com/ndk/guides/jni-tips#native-libraries)；符号隐藏的适用范围见 [NDK 符号可见性说明](https://developer.android.com/ndk/guides/symbol-visibility)。隐藏符号不等于隐藏指令，也不阻止已控制进程的分析者观察注册地址，不能宣传为防反编译或防脱壳。

已公开 rc.3 不变；交付版本另由维护者确认，不为本项移动标签或增加新的日常重型 CI。

## 基线盘点

2026-10-23，本机上一阶段构建的标准／工控资源中，四 ABI 的已定义对外动态符号均只有 `JNI_OnLoad`，没有普通 `.symtab` 或 DWARF 调试节，没有原始桥接类名；Native 不声明固定 SONAME。当前导出面已经很小，本项主要防止后续回归，不新增另一个“隐蔽入口”。

标准资源已将 Cargo 源码位置规范化为 `.cargo/registry/...`。工控 v7a 构建只映射项目根目录，仍在依赖的 panic 位置中留下构建机用户目录；本阶段修复该构建差异。文档、错误和审计报告不复制泄漏的具体用户名路径。

## 架构边界

按 L2 构建契约变更处理：增加独立、仅用 Python 标准库的 ELF 审计模块，由现有 `scripts/stub_bindings.py audit` 调用；三个构建入口继续共享同一条交付检查。不在 GUI 或 `shield-core` 增加 ELF 解析器，不引入新 crate、外部包或用户运行依赖。

审计模块只接收 Native 字节与预期 ABI，返回可序列化的最小检查结果；未知格式、非法索引或不符合契约时抛出明确错误，由现有构建入口停止打包交付。只读解析，不改写 ELF。已有 JNI 绑定摘要用于核对同批资源，不变成安全认证凭据。

## 构建检查

- 解析 ELF32／ELF64 的小端共享库格式，核对 ARM、ARM64、x86、x86_64 对应的机器类型和位宽；格式截断、越界、字符串缺结束标记、异常表项大小或缺失动态符号表均失败。
- 区分未定义的系统导入与已定义导出，只允许一个全局、可见、可执行节内的 `JNI_OnLoad` 函数。其他全局／弱／唯一可见导出均失败，不能把导入列表误报为业务接口。
- 按 ELF 节类型拒绝普通符号表，即使该节被改名；拒绝 `.debug_*`、`.zdebug_*` 及 `.gnu_debugdata` 等实际调试内容。保留 `.eh_frame`、`.ARM.exidx`、构建 ID 等正常加载或故障定位信息。
- 检查 Native 中的构建机用户目录路径及原始 JNI 桥接包路径，发现时失败；只输出命中的类别，不回显本机用户名或完整绝对路径。
- 标准和工控构建均规范化项目、Cargo、Rustup 根路径，尊重构建者配置的 `CARGO_HOME`、`RUSTUP_HOME`；不修改 SDK、全局环境或用户源文件。

Bash 两个入口共享 `scripts/native-build-flags.sh`，Windows Git Bash 先用 `cygpath` 转成 Rust 实际记录的本机路径；PowerShell 使用本机路径数组。两者均采用 [Cargo 的参数分隔编码](https://doc.rust-lang.org/cargo/reference/environment-variables.html)，不再依赖按空白拆分的 `RUSTFLAGS` 拼接，避免带空格或中文的源码路径拆成多个参数。

不增加宽泛的“禁止所有路径／所有可读字符串”规则。Android 类名、方法签名、系统路径、反调试／Root 检查依据与第三方错误不能机械删除，否则可能破坏兼容或诊断。

本检查只解析所消费的 ELF 表与已列明路径类别，不是对任意 ELF 的完整加载器验证，也不证明不存在其他未知静态线索；实际运行继续由 JNI 和设备回归覆盖。

## 字符串分类与处理

| 类别 | 本阶段处理 | 原因 |
|---|---|---|
| 构建机用户名和本机源码绝对路径 | 构建期规范化，残留时拦截 | 与运行无关，泄漏构建环境 |
| 原始桥接包路径、意外品牌字符串 | 前者拦截，后者分类报告并复核 | 区分已确认契约与其他合理来源，不盲目替换二进制 |
| 规范化的依赖源码相对路径、匿名 Rust 工具链路径 | 保留并分类报告 | 不含构建者用户名，可能用于 panic 定位 |
| JNI 类名、方法签名、Android 系统调用字符串 | 保留 | 动态注册和系统互操作所需，不伪装成不存在 |
| Native 注入、载荷、解密及解压失败上下文 | 保留，记录源码位置 | 现有排障依赖这些信息，本轮不为减少字符串而丢失原因 |
| Manifest 品牌字段及缓存目录 | 不在本阶段改动 | 属于跨模块运行契约，沿用[壳标识后续规划](stub-identity.md)单独评审 |

当前 Native 诊断主要位于 `shield-stub/src/main/rust/src/lib.rs` 的 JNI 调用、数组构造和 Native 失败转 Java 反射路径，以及 `bin_loader.rs` 的格式、认证和解压错误。本阶段不更换错误码、不吞异常、不去掉原有失败关闭或兼容回退。

## 本地实施与验收

2026-10-23，本阶段没有修改任何 Java／Rust 运行时代码、Cargo 依赖、版本号、用户配置或远端数据库。新增 `scripts/native_surface.py` 负责 ELF 检查，现有绑定审计仅编排调用；两个 Bash 编译入口共享路径参数函数，PowerShell 保留其本机参数构造和环境恢复方式。

- `python3 -m unittest discover -s scripts/tests -v`：44 项通过，包含四 ABI 结构夹具、额外全局／弱／唯一导出、隐藏或非函数入口、调试内容、改名普通符号表、损坏的表与字符串索引、路径隐私、中文空格参数及资源审计顺序。
- 用新增审计检查旧工控资源时，确实因构建机路径残留而失败；修复后执行 `SHIELD_VERSION=1.4.2-rc.3 make build-stub`，r29 标准与 r25c／Rust 1.77.2 工控库实际重编译，标准／工控／内部内存候选资源的所有 ABI 均通过新检查。没有在二进制上直接覆盖字符串。
- 三套资源的动态导出均只有 `JNI_OnLoad`，普通符号表和调试信息未带入；工控 v7a 的构建机用户目录残留已消除。规范化的 Cargo 相对路径、匿名 Rust 工具链路径、系统 JNI 签名和原有运行错误上下文按设计保留。
- `make audit-stub-dex` 与 `cargo fmt --all --check` 通过；JNI 本机 JVM 探针注册与调用通过。由于没有修改 Rust／Java 运行逻辑，本轮不把上一阶段全部业务单测标成重新执行。
- 一加 8 的系统报告为 Android 17／API 37、4 KB，ADB Root 调试保持原状。标准和工控资源分别通过真实双 DEX、混合 ABI 确认排除、签名、未加固基线、同签名覆盖安装和 ARM64 首次／缓存启动。工控包再强制 ARMv7 安装并确认 `app_process32`，清数据后的双 DEX／远程进程启动和缓存 inode／长度／修改时间复用通过。
- `cargo tauri build --bundles app` 生成完整 macOS `.app`，完整应用 adhoc 签名与严格校验通过，包内标准／工控资源再次通过新审计。它仍显示工作区版本 `1.4.2-rc.3`，不是重新发布的 rc.3。

剩余边界：本轮没有运行 Windows／Linux 原生桌面构建，没有补测 Android 4.4、API 21／23、Android 9 专项、16 KB 或 x86 设备；Root 严格策略的热缓存拒绝沿用上一阶段真机记录，本轮未重复执行。没有增加普通提交的重型 CI 或 CLI 发布任务。
