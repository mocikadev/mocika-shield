# Manifest 运行字段去品牌化

## 目标与边界

维护者已确认采用固定中性字段与新资源协议。消除壳自己写入的 Manifest 品牌字段，统一核心写入与 Java 读取；不做业务 APK 全文替换，也不宣称因此无法识别或分析加固。

不改 GUI、CLI 参数、用户配置、数据库、统计、DEXB v5、缓存摘要算法或目录、Native ABI 和加载策略。原包中其他业务字段与字符串保留。当前公开的 `1.4.2-rc.3` 不变，交付版本在整阶段验收后另行确认。

## 现状与方案取舍

变更前由 `protect/manifest.rs` 写入七项元数据，`StubApp`、`RuntimeSecurity`、`DexCache` 与内部内存候选读取。其中六项带 `dev.mocika.shield`，另一项为 `ORIGINAL_APPLICATION`。旧壳读取环境策略异常或字段缺失时会返回兼容策略，原 Application 读取失败会回退系统 Application；名称错配可能悄悄改变行为，不能把它们视作文案替换。

| 方案 | 兼容与成本 | 结论 |
|---|---|---|
| 固定中性字段，新旧资源协议明确区分 | 新核心保留旧资源写法；旧核心拒绝新资源；新壳不携带旧字段 | 采用，改动和失败边界可验证 |
| 新旧字段双写或壳侧双读 | 保留现有名称并增加优先级、重复与冲突规则 | 不采用，仍留下品牌特征 |
| 每次任务随机字段并联动 DEX 改写 | 需新增占位槽、合法 DEX 重写和冲突规则 | 暂不实施，不与固定字段治理混合 |

按架构级协议变更执行；实现不得擅自改为动态随机化、双写或忽略未知协议。

## 单一字段定义与职责

字段与协议号由 `shield-stub/runtime-manifest-contract.json` 定义。平台无关的 Python 工具生成仅含当前字段的 Java 常量，以及同时包含新旧字段的 Rust 私有常量；生成文件随源码提交并通过一致性检查。生成器不参与用户加固运行，不新增运行依赖或 crate，不把旧字段带入 Java 常量。

| 语义 | 旧字段 | 新字段 |
|---|---|---|
| 原 Application | `ORIGINAL_APPLICATION` | `rt.app` |
| 环境策略 | `dev.mocika.shield.ENV_POLICY` | `rt.policy` |
| 原组件工厂 | `dev.mocika.shield.ORIGINAL_COMPONENT_FACTORY` | `rt.factory` |
| 缓存格式 | `dev.mocika.shield.CACHE_SCHEMA` | `rt.cache.schema` |
| DEX 数量 | `dev.mocika.shield.CACHE_DEX_COUNT` | `rt.cache.count` |
| 缓存根摘要 | `dev.mocika.shield.CACHE_ROOT_SHA256` | `rt.cache.root` |
| 内存候选载荷字节数 | `dev.mocika.shield.PAYLOAD_DEX_BYTES` | `rt.payload.bytes` |

固定中性名称仍是静态特征，不作为秘密、认证数据或防脱壳能力。原包占用所选协议的保留字段时必须在写入和业务 DEX 加密前拒绝，不覆盖、不删除、不静默复用；不同组件下不冲突的同名字段与业务字符串不应误删。

核心的 `RuntimeMetadata` 根据资源协议选择不可变字段集合，经 `RuntimeSelection` 传入现有 Manifest 写入边界。GUI 和 CLI 不维护第二套规则。Java 只消费生成的当前常量；安全策略、Application、缓存和内存预算仍各自拥有既有业务规则，不集中为新的全局状态或万能运行时服务。

## 协议与兼容

| 核心与资源组合 | 行为 |
|---|---|
| 新核心与旧标准／工控协议 2 | 使用旧字段，保留既有功能与能力校验 |
| 新核心与旧内部内存候选协议 3 | 使用旧字段，仍要求显式内部资源入口 |
| 新核心与新标准／工控协议 4 | 只写中性字段 |
| 新核心与新内部内存候选协议 5 | 只写中性字段，不恢复内存 DEX 产品排期 |
| 旧核心与协议 4／5 | 既有严格协议检查明确拒绝，提示更新配套工具 |
| 任意未知协议或能力组合错配 | 加固前失败，不猜测、不兼容回退 |

协议号表示桌面核心与壳资源的消费契约，不是 DEXB 或缓存格式版本。`cache_schema=1`、原始 DEX 顺序、长度和摘要算法保持不变，缓存目录继续由应用版本与根摘要决定。只改变字段名称不应使同一业务载荷的既有缓存失效。

构建脚本从同一协议定义取得标准／内存候选协议，不在 Bash 与 PowerShell 手写第二套号段。工控资源继续复用标准 DEX 和映射，仅替换 v7a Native；资源审计核对协议、最终 DEX 所含字段及标准／工控一致性，未知或错配资源不得更新自动发现入口。

## 读取与失败策略

- 新壳必须读到合法的 `compatible` 或 `strict`；缺失、错误类型、未知值或读取异常明确失败，不能退回兼容模式。环境检查仍在每次进程启动、缓存判断之前执行，Root 拒绝仍使用既有提示链路。
- 原 Application 必须存在且为非空字符串；原包没有自定义 Application 时，核心显式写入 `android.app.Application`。字段缺失不假装业务初始化成功。
- 原组件工厂保持可选；有值时验证其类型和内容，不改变组件实例化的接管顺序。
- 缓存身份继续校验格式、DEX 数量和根摘要；不把字段缺失视作有效缓存。内存预算沿用既有安全回退规则，不放宽状态协议。
- 错误使用固定代码／现有任务错误边界，不记录密钥或上传 APK；不为去品牌化吞掉错误。

## 回滚

以桌面核心和同批全部壳资源为交付单位回滚，不单独替换 Manifest、DEX 或某个 ABI 的库。新核心保留旧协议读取是维护回退能力，不意味着旧核心可以消费新资源。已生成的新 APK 不依赖桌面核心持续运行；新问题通过重新加固和新版本交付处理，不覆盖已公开标签。

## 本地实施与验收

2026-10-23，按上述协议完成实现，未增加运行依赖、用户设置或数据库字段。`manifest_keys.rs` 和 `ManifestKeys.java` 是声明投影；`RuntimeManifest` 只负责读取当前元数据与必要字符串校验，不拥有环境策略或缓存状态。读取失败、必要字符串无效与策略非法分别使用 `T01`、`T02`、`S02`，实际环境拒绝仍为 `S01`。

- `python3 -m unittest discover -s scripts/tests -v`：50 项通过，含生成一致性、新旧字段、非法定义、实际 DEX 字符串与协议错配守门。`cargo fmt --all --check`、`git diff --check` 和相关 Shell 语法检查通过。
- `cargo test -p shield-core -p shield-cli`：核心 179 项、CLI 5 项、核心集成 5 项通过；既有外部条件忽略项保留。核心／CLI 的全目标严格 Clippy 通过。GUI 后端 108 项通过、3 项按原有条件忽略。
- `testDebugUnitTest`：Java 44 项通过，新增缺失、空值、错误类型及未知策略不降级的用例；JNI 本机 JVM 探针注册与调用通过，不将其代替 Android 运行。
- `SHIELD_VERSION=1.4.2-rc.3 make build-stub` 实际生成协议 4 的标准／工控资源和协议 5 的内部候选资源，全部 ABI 通过 JNI／Native 暴露面及 Manifest 字段审计。Stub DEX 为 30,104 字节、22 类、299 方法、52 字段、484 字符串，原有上限不变。
- 使用变更前保存的旧核心消费新标准资源，明确拒绝 `Runtime` 协议 4，未生成输出；新核心使用公开 rc.3 的旧标准／工控资源加固成功，不将单元解析通过冒充旧内部内存候选的设备验收。
- 一加 8 系统报告 Android 17／API 37、4 KB，ADB Root 调试保持原状。标准和工控各自的 ARM64／ARMv7 四组均通过旧壳首次启动、同签名覆盖新壳、强停重启、清数据重新解密及双 DEX／多组件／远程进程启动。核对实际 `app_process64`／`app_process32`；覆盖和热启动时两份缓存的路径、长度、inode、修改时间不变。
- 工控 ARMv7 热缓存上覆盖严格策略包，出现 `SecurityException: S01` 且无业务 Application 成功标记；恢复兼容策略正常运行。此为日志验证，不是拒绝提示的视觉复验。
- 对真实工控加固 APK 移除有效策略键后重新打包、对齐、同证书签名并覆盖安装，热缓存下出现 `SecurityException: S02`，业务未启动，缓存路径、长度、inode 和修改时间未改变；恢复正常包后重新启动通过。确认策略缺失并非只在纯函数测试中拒绝。
- 工控混合 ABI 的无设备端到端回归通过，覆盖未确认排除时拒绝、显式排除旧 ABI、保留主流 ABI 业务库字节、签名、解包 Manifest 和 `extractNativeLibs=false` 打包检查。

- `cargo tauri build --bundles app` 生成完整 macOS `.app`，本地 adhoc 签名与严格校验通过；包内标准／工控 ZIP 再次通过完整审计。仍显示工作区版本 `1.4.2-rc.3`，未替换公开安装包。

### 后续改动的系统兼容性判断

从 rc.3 到当前主线的相关改动没有引入更高版本 Android API 依赖，没有改变双 NDK、最低 API、ABI、Dalvik／ART 分流、DEXB 或业务 DEX 加载方式。JNI 仍沿用原有 `JNI_OnLoad`／`RegisterNatives`，只统一同批名称、方法签名和构建审计；Manifest 使用原有元数据读取机制，核心与壳侧按资源协议成对选择字段。新增的字段缺失／非法时明确失败属于校验收紧，不是系统版本要求提高。

本阶段主要风险为映射、签名、字段与资源错配，应以契约审计、JNI 探针、真实 32／64 位启动、覆盖安装、缓存、安全策略和 16 KB 回归验证，不因名称治理重新启动整套四系统验收或让用户反复测试。当前主线未重新实测 Android 4.4 的事实继续保留，但不将旧模拟器恢复或完整矩阵复测新增为交付前置条件。本轮停止环境改造，按现有证据收口。
