# DEX 结构与方法代码分离研究

本文记录 Mocika Shield 在完整 DEX 加密和内存加载之后的后续保护研究方向：将 DEX 元数据与方法代码分离，使攻击者取得某个壳文件、缓存文件或单次内存快照后，不能直接得到可交给常规工具使用的完整业务 DEX。

本文只定义研究目标、依赖条件和原型门槛，不代表当前已经支持，也不预先承诺正式版本号。

## 参考实现审查结论

[dpt-shell](https://github.com/luoyesiqiu/dpt-shell) 已验证“抽离方法指令、保留结构载体、运行时恢复”在工程上可行。其处理端从 DEX `code_item` 提取 `insns`，原位置写入符合返回类型的占位指令；运行端通过 Hook `mmap`、ART `DefineClass` 等函数，在类加载时把指令写回内存。

本项目只借鉴以下设计思想：

- 方法声明、字段和类型等结构信息与方法指令分离。
- 使用稳定的 DEX、类和方法身份建立代码载荷索引。
- 对不适合处理的启动、反射、JNI 和框架敏感代码提供明确排除规则。
- 用按 DEX 或类组组织的认证加密载荷提高单一载体的恢复成本。

不直接移植其 Java 处理器、Native Hook 框架、加密实现或运行时补丁代码。即使参考代码采用宽松许可证，正式实现仍使用 Rust 独立设计和验证，避免引入旧解析器、第三方 Hook 框架及其系统兼容负担。

### 安全软件反馈

dpt-shell 已有多类误报反馈，包括 VirusTotal 检出、手机厂商安全检测拦截和应用市场上架受影响。维护者在 [Issue #51](https://github.com/luoyesiqiu/dpt-shell/issues/51) 中确认检测与 Hook 系统函数有关；[Issue #128](https://github.com/luoyesiqiu/dpt-shell/issues/128) 显示固定 `ProxyApplication` 也形成了可识别特征；[Issue #170](https://github.com/luoyesiqiu/dpt-shell/issues/170)、[Issue #173](https://github.com/luoyesiqiu/dpt-shell/issues/173) 和 [Issue #187](https://github.com/luoyesiqiu/dpt-shell/issues/187) 还反映出签名信誉、固定壳特征及 Native ELF 扫描会共同影响检测结果。

这些反馈不能简单归因于“加固工具必然误报”。以下行为与恶意加载器、注入框架和外挂高度相似，属于本方向的高风险信号：

| 行为 | 风险 | 本项目决定 |
|------|------|------------|
| Hook `mmap`、`DefineClass`、`LoadClass` 等系统或 ART 私有函数 | 劫持类加载和系统调用是常见启发式检测特征，且依赖系统版本和厂商实现 | 禁止进入正式方案 |
| 搜索、解析并调用 `libart.so` 私有符号 | 容易形成稳定静态特征，系统升级后兼容成本高 | 禁止进入正式方案 |
| 将代码页改为可写且可执行，运行时改写或解密 Native 指令 | 与自修改代码、内存载荷执行行为相似 | 禁止进入正式方案 |
| 运行时回填 DEX 指令 | 即使业务合法，也可能被识别为动态代码修补 | 只有找到不依赖私有 Hook 的路径才允许研究 |
| 反 Frida、进程扫描和主动对抗分析工具 | 与动态加载、反调试叠加后显著提高可疑度 | 本方向不新增或扩张；现有运行时检查单独维护和评估 |
| 固定壳类、固定 Native 库名和固定二进制片段 | 容易被签名规则批量标记 | 保持中性命名和冲突规避，但不以持续变形绕过检测 |
| 每次使用临时签名或复用信誉不明的测试签名 | 可能影响厂商和安全服务的信誉判断 | 正式验证固定使用稳定测试签名或用户正式签名 |

随机包名、加密 Hook 代码或持续改变二进制特征只能短期影响静态规则，不能消除高风险运行行为，还会使实现更接近规避检测的恶意壳。本项目不以绕过安全软件为目标；检测新增时优先删除或替换风险行为。

## 背景

当前保护流程以完整 DEX 为加密单元：

```text
完整业务 DEX
  → 压缩并整体加密
  → 启动时整体解密
  → 形成系统可加载的完整 DEX
  → 文件或内存注入
```

这种方案能够阻止直接从 APK 静态提取业务 DEX，但一旦攻击者控制 Root 环境、绕过检测并取得运行时完整明文，后续分析门槛会明显降低。Root 检测、缓存完整性和内存 DEX 分别减少常见提取机会，但不能改变“某一时刻存在完整可执行 DEX”的基本事实。

后续研究的核心不是简单破坏 DEX 文件头，而是改变保护载荷和运行时恢复粒度。

## 目标

- APK 内不保存能够直接还原全部业务实现的完整可执行 DEX。
- 提取到结构载体时，方法实现仍缺失或不可直接使用。
- 优先在内存中完成必要恢复，避免重新形成持久明文 DEX。
- 通过分片或按需恢复缩短全部方法代码同时明文存在的窗口。
- 保持真实 Application、多 DEX、Kotlin、ARouter、反射、JNI 和异常处理的语义。
- 用可复现样本和兼容数据决定是否继续，不以“常规工具打不开”作为唯一成功标准。

## 非目标与安全边界

- 不宣称能够阻止已完全控制进程、内核或 ART 的攻击者。
- 不把修改 magic、checksum、header 或 section 偏移等表层损坏单独视为有效保护。
- 不在完整内存 DEX 路径稳定前直接实现方法级恢复。
- 不在首个原型中支持 Android 4.4～9、全部 DEX 变体或所有厂商系统。
- 不在没有性能和兼容证据时实现 Native 虚拟机或大规模方法虚拟化。
- 不直接修改 DEXB v5。任何新载荷布局必须使用新协议并设计明确的版本拒绝和迁移规则。
- 不依赖 `ArtMethod` 等 ART 私有结构的运行期 Hook 来回填或擦除方法代码；该路径高度依赖 Android 版本、厂商实现、编译模式和并发时序。
- 不 Hook `mmap`、`DefineClass`、`LoadClass` 或其他系统和 ART 私有函数。
- 不把可写且可执行内存、自修改 Native 代码或运行时解密 Native 代码段作为恢复手段。
- 不在本方向新增反 Frida、分析工具进程扫描或隐藏 Hook 行为；现有运行时检查不与方法代码分离同时扩张。
- 不为了降低安全软件检出而持续随机化、加密或变形壳实现。
- 不把 DEX 内存页强制设为“仅执行”作为方案前提；ART 的校验、解释执行、编译与垃圾回收仍可能需要读取相关数据。
- 不通过抹除 DEX 魔数、校验和或表偏移制造表面损坏；这类修改容易机械修复，也可能破坏延迟类加载和系统校验。
- 不把自定义 ELF 动态链接器作为本方向的依赖；自行实现重定位、线程局部存储、异常展开和厂商兼容的成本远高于当前收益。

只要代码最终需要执行，理论上仍可能从执行环境恢复。该方向的目标是提高批量脱壳、完整重建和自动化分析成本，而不是建立不可恢复的客户端秘密。

## 研究层级

### 结构载体与代码载荷分离

加固端解析 DEX，将类、字段、方法声明等结构信息与方法 `code_item` 分开保存；结构载体不包含完整业务方法实现，代码载荷单独认证加密。

候选流程：

```text
原始 DEX
  → 解析并建立稳定方法索引
  → 生成结构载体
  → code_item 分片、认证并加密
  → 运行时校验索引和载荷
  → 仅在内存中重建可加载 DEX
```

该层能够阻止提取结构载体后直接获得完整代码，但内存重建完成时仍可能出现完整 DEX，因此它是第一阶段，不是终点。

### 分片恢复

将方法代码按 DEX、类组或固定大小分片，运行时只解密当前加载阶段需要的分片。必须先证明分片边界不会破坏：

- 方法索引和跨 DEX 引用。
- try/catch、调试信息和 switch/array payload。
- Kotlin 协程、默认参数与合成方法。
- 反射、动态代理、JNI 注册和序列化框架。
- ART 校验、JIT/AOT 与垃圾回收后的延迟类加载。

分片恢复仍可能被持续监控汇总，不应描述为防 Dump，只能减少单次快照直接获得的完整度。

### 按需方法恢复

只在方法即将执行时恢复对应代码，使用后清理或重新加密。该层涉及 ART 内部结构、并发、可执行内存和系统版本差异，维护成本显著高于完整 DEX 内存加载。

只有结构分离和分片恢复已经稳定，且存在明确用户价值时才进入可行性研究；不得直接进入生产路线。

### 关键方法虚拟化

把少量关键方法转换为自定义指令并由 Native 解释执行，可以进一步避免原始 DEX 指令进入 ART，但会引入新的执行引擎、性能成本和攻击面。

当前只保留概念位置，不制定实现任务。首轮研究明确排除通用虚拟机保护。

## 方案取舍

| 方案 | 收益 | 主要问题 | 决定 |
|------|------|----------|------|
| 只制造损坏 DEX | 实现相对简单，常规工具可能报错 | 文件头容易修复，不改变完整代码已存在的事实 | 不作为独立方案 |
| 完整 DEX 内存重建 | 不持久落盘，能复用系统加载 | 内存中仍存在完整 DEX | 作为结构分离的前置能力 |
| 结构与代码分离后内存重建 | 提取单一载体不能直接获得完整代码 | 需要可靠解析、重建并改变载荷协议 | 首个研究原型 |
| 分片或按需恢复 | 降低单次提取完整度 | ART、并发、性能和系统兼容风险高 | 原型成功后再评估 |
| 通用 Native 虚拟机 | 关键代码不以原 DEX 指令执行 | 开发维护成本和性能风险最高 | 当前不采用 |

## 启动条件

离线研究原型可以在不改变正式运行时的前提下独立启动，必须满足：

1. `1.3.0` 的缓存安全、资源能力协议和环境策略已经稳定。
2. 原型只读写独立测试文件，不接入 `protect_apk()`、DEXB v5、正式 Stub、CLI 或 GUI。
3. 使用自有合成样本或明确允许公开分析的样本，不上传用户 APK 到第三方扫描服务。
4. 原始 DEX 必须作为测试基准保留，能够逐项比较处理前后的结构和行为。

运行时原型另有门槛：完整内存 DEX 不必先成为正式功能，但必须已经明确其长期内存成本；结构分离不得被用来绕过该问题。只有离线往返、兼容样本和静态保护收益全部通过，且存在不依赖 ART 私有 Hook、可写可执行内存和自修改代码的恢复方案时，才能申请进入运行时研究。

## 下一阶段可行方案

下一阶段只实现宿主端离线原型，按三个可独立停止的阶段执行。

### 方法指令清点与只读解析

在 `shield-core` 内建立可删除的私有研究模块，只读取单 DEX 并输出方法清单，不生成加固 APK。

输出至少包含：

- DEX 身份和方法索引。
- 声明类、方法名、原型和访问标记。
- `code_off`、`insns_size`、异常表及调试信息存在性。
- 方法是否可处理，以及跳过的确定原因。

首轮只覆盖普通 Java 方法，明确跳过 Native、Abstract、构造和静态初始化、指令空间不足及无法完整解析的方法。跳过规则必须由解析结果决定，不允许失败后静默处理。

完成标准：同一输入重复输出完全一致；错误偏移、截断数据和异常长度均返回结构化错误；现有正式加固行为没有变化。

完成结果（2026-07-31）：

- 已在 `shield-core` 建立仅测试构建启用的私有 `dex_research` 模块，不进入正式库、加固入口和发布产物。
- 已只读解析 DEX header、字符串、类型、原型、方法、类数据和 `code_item`，输出方法身份、原型、访问标记、指令长度、异常表与调试信息状态。
- 已区分普通候选、Native、Abstract、构造、静态初始化、缺少代码、指令空间不足和寄存器不足。
- 合成单 DEX 已覆盖稳定清单、截断表和未对齐 `code_item`；仓库 Android 冒烟工程实际编译的 DEX 已完成一次本地清点验证。
- 没有新增依赖、公共接口、配置字段或文件写入行为。

### 离线抽取与往返恢复

在临时副本上提取候选方法的 `insns`，写入类型正确的占位实现，并生成仅供测试的独立代码载荷。随后离线恢复成完整 DEX，修复必要的 DEX 校验字段。

本阶段不加密载荷、不设计正式协议，先验证“抽取—占位—恢复”的数据正确性，避免把解析缺陷和密码协议问题混在一起。

完成标准：

- 恢复后的方法指令、异常表和关联元数据与原始 DEX 逐项一致。
- 原始、占位和恢复后的 DEX 均能被独立解析。
- 合成测试应用在恢复前表现为预期占位行为，恢复后与原应用一致。
- 失败不会覆盖原文件，也不会产生可被正式加固流程误用的资源。

完成结果（2026-07-31）：

- 已新增独立的私有转换子模块，接收不可变 DEX 字节并返回占位载体与内存测试载荷，不读写文件。
- 只抽取清点结果为普通候选的方法；构造、静态初始化、Native、Abstract 和其他跳过项保持原样。
- 已为 void、普通基本类型、对象、数组和宽类型返回值生成类型匹配的占位指令，剩余指令空间写入 `nop`。
- 测试载荷记录方法索引、指令位置、原始内容和占位内容，并绑定占位载体 SHA-256；恢复前校验载体大小、摘要、区段边界、重叠和占位内容。
- 抽取和恢复都会重新计算 DEX SHA-1 signature 与 Adler-32 checksum；合成 DEX 已完成逐字节往返测试。
- 仓库 Android 冒烟工程的 8304 字节真实 DEX 共抽取 19 个候选方法；占位载体与恢复产物均通过 Android `dexdump` 解析，恢复产物 SHA-256 与原始 DEX 完全一致。
- 当前只证明结构正确和离线可逆；占位载体的预期运行行为及恢复产物的实际运行语义仍由下一阶段验证。

### 兼容样本与静态收益评估

离线往返稳定后扩大测试，不接入 Android Stub：

1. 普通调用、继承、接口、同步方法、异常和反射。
2. switch、数组载荷、try/catch 和不同返回类型。
3. Kotlin Lambda、默认参数、合成方法和协程。
4. R8、ARouter、JNI 声明及多 DEX 只读解析。
5. 使用常规 DEX 工具比较原始载体和占位载体可恢复的业务实现比例。

完成后召开一次明确的继续/停止评审。只有结果证明结构载体不能通过机械修复直接恢复完整方法实现，且跳过比例没有使保护收益失去意义，才设计认证加密载荷和运行时方案。

首批 Java 可执行语义结果（2026-07-31）：

- Android 冒烟工程新增独立业务样本类、未抽取观察入口和状态持有类；转换器只选择业务样本类，Application、Activity 与观察入口保持原始实现。
- 覆盖 int、long、对象、数组、boolean、double、void 副作用、switch、try/catch 和 synchronized 方法，共抽取 10 个普通候选方法。
- 原始、占位和恢复 DEX 分别装入同一测试 APK，并使用同一调试证书签名；三种 APK 均通过签名校验、安装和冷启动。
- API 35 ARM64 真机和 API 33 ARM64 真机结果一致：原始与恢复产物输出完全相同；占位产物稳定输出各返回类型默认值，void 副作用不发生，应用未崩溃。
- 该结果证明“选择业务类—写入占位—Android 实际执行—离线恢复”的首个 Java 闭环成立，不代表 Kotlin、R8、ARouter、JNI 或多 DEX 已经兼容。

R8 与反射扩展结果（2026-07-31）：

- Android 冒烟工程新增独立的 `dexResearch` 构建类型，继承发布构建并启用 R8；该构建类型只服务本研究，不改变正常调试和发布构建。
- 观察入口通过 `Class.forName` 和反射调用业务样本；研究专用 R8 规则仅保留被选择业务类的身份和公开静态方法，其余测试组件仍由 R8 正常处理。
- 对 R8 生成的单 DEX 只抽取该业务类的 10 个候选方法，原始、占位和恢复 APK 使用同一调试证书重新签名。
- API 35 ARM64 与 API 33 ARM64 真机结果一致：原始与恢复产物的 10 项语义输出完全相同；占位产物只返回类型正确的默认值，且三种产物均未崩溃。
- 该结果证明转换器能够处理当前 R8 产物，且保留类身份时反射调用不被占位与恢复破坏；它不代表已经支持根据任意混淆映射自动定位业务类。后续若允许选择被混淆类，必须以 R8 最终描述符或映射文件建立稳定身份，不能依赖源码类名猜测。

Kotlin 扩展结果（2026-07-31）：

- 冒烟工程使用 Kotlin 2.2.20 生成默认参数桥接、Lambda、数据类合成方法以及真实挂起后恢复的协程状态机；这些内容只存在于研究测试构建。
- R8 后的 Kotlin 样本类及编译器生成类共抽取 24 个候选方法。API 35 与 API 33 ARM64 真机上，原始和恢复产物均输出 `default=盾4,lambda=26,synthetic=12,suspend=22`，占位产物稳定输出对应默认值，应用未崩溃。
- 另行只抽取协程状态机的 `invokeSuspend` 方法并保留调用链其他部分：占位产物在两台设备上均得到可观察的协程空结果异常，恢复产物重新得到 `suspend=22`，证明状态机方法实际经过执行，而不只是完成了离线字节比较。

静态保护收益评估（2026-07-31）：

- 仓库研究样本包含 2 个 DEX、614 个声明方法，其中 415 个方法可按当前保守规则抽离，占全部声明方法 67.59%；可抽离指令为 26166 字节，占全部方法指令 85.87%。

- 真实样本跳过项包括 118015 个构造方法、18791 个静态初始化方法、534 个 Native 声明、20836 个 Abstract 声明和 880 个其他不满足安全转换条件的方法。构造与静态初始化仍保留原始实现，是当前静态残留的主要来源。
- 使用 jadx 1.5.5 对仓库样本比较，类、字段、方法签名、注解、字符串和包结构仍然可见，但候选方法只剩类型正确的默认返回或空副作用；例如固定数字、字符串、分支、数组内容与状态写入已不能从载体方法体直接恢复。
- 使用同一工具比较真实样本首个 DEX，原始文件有 20 个反编译错误，占位载体有 2245 个。该增长主要说明当前原型覆盖指令后仍保留异常表和调试结构会干扰控制流分析，不能作为正式安全效果；正式结构载体必须保持内部自洽，不以工具报错或畸形控制流作为保护手段。
- 占位转换保持 DEX 文件长度不变，因此包体积没有收益；结构载体仍暴露完整类型关系、接口、字段、方法签名、注解、字符串和未抽离方法。它提高的是批量取得普通方法实现的成本，不是隐藏应用结构，也不能阻止已控制运行时的持续提取。

继续/停止评审结论：当前保守规则仍可移除两个样本约 86% 的方法指令字节，跳过比例没有使静态收益失去意义；只取得结构载体时也无法通过修复 header、checksum 或少量偏移机械恢复已被抽离的指令。因此离线方向通过继续门槛，可以设计认证的整组载荷清单及篡改/错序拒绝测试。该结论不授予运行时接入资格：在找到不依赖 ART 私有 Hook、系统函数 Hook、可写可执行内存或自修改代码的恢复路径前，不实现正式 Stub、APK、CLI 或 GUI 能力。

加密代码载荷封装结果（2026-07-31）：

- 新增测试私有 `bundle` 模块，负责把认证整组清单及每个 DEX 的代码载荷规范编码后整体使用 ChaCha20-Poly1305 认证加密；单 DEX 解析、占位和恢复仍由 `transform` 负责，集合身份规则仍由 `manifest` 负责。
- 外部恢复输入只包含有序 DEX 身份和占位载体。解封后解析代码载荷，先核对成员数量与身份顺序，再由单 DEX 恢复器验证载体摘要、方法区间和占位内容，最后用恢复结果重建整组清单并与密文内清单比较。
- 研究格式显式包含 magic、版本、清单长度、DEX 数量、DEX 身份、原始长度、载体摘要、方法数量以及每个方法的索引、偏移、原始指令和占位指令；未知版本、截断及尾随数据全部拒绝。
- 解析预算暂定为最多 256 个 DEX、每个 DEX 最多 200 万条方法记录、单段方法指令最多 16 MiB、整组明文最多 256 MiB、DEX 身份最多 1024 字节。编码前预计算总长度，解密前限制密文长度，解析每个变长字段时先核对剩余长度与单项预算再分配。
- 双 DEX 纯内存测试已经完成“抽取—整组编码加密—仅持有占位载体—认证解封—逐字节恢复”闭环，并覆盖错误密钥、密文篡改、载体错序和载体缺失；解析器另行覆盖 magic、版本、截断、尾随数据、超长字段、DEX 数量及总明文预算。
- 当前 nonce 由研究调用方提供，测试为保证确定性使用固定值。正式方案必须使用安全随机且同一密钥下不重复的 nonce，并设计密钥派生、nonce 存储及版本迁移；本阶段不冻结这些规则。
- 整体加密要求完整密文和明文同时参与解封，适合验证字段与失败语义，不代表运行时可接受的峰值内存。正式研究若继续，必须先对真实多 DEX 样本测量编码体积、解封峰值和解析耗时，再决定是否需要逐 DEX 独立认证分片。

真实样本资源成本评估（2026-07-31）：

- 新增显式忽略的本地研究入口，按自然顺序读取 `classes*.dex`，完成抽取、封装、仅凭占位载体解封恢复及逐字节核对。使用优化构建测量阶段耗时，通过进程 RSS 检查点和系统计时器观察内存；该口径是 macOS 宿主端方案对比，不代表 Android 启动性能。
- 仓库双 DEX 样本共 107300 字节，抽取指令 26166 字节；首轮整组密文为 59346 字节，读取、抽取、封装和解封恢复分别约 1、2、3、3 毫秒，证明测量入口本身能够完成正确闭环。
- 已授权真实样本包含 12 个 DEX、118708156 字节，抽取指令 30111218 字节。首轮格式同时保存原始指令与占位指令，整组密文达到 68347120 字节；占位指令已经被载体摘要认证，重复保存没有额外安全收益。
- 研究封装升级后不再序列化占位指令。解封时先验证载体长度和 SHA-256，再从认证载体的对应方法区间重建占位内容，继续复用单 DEX 恢复器校验。真实样本密文降至 36205246 字节，为原始 DEX 总量的 30.50%，相对首轮减少 47.03%。研究格式版本和认证附加数据同步升级，旧研究密文不会被静默接受。
- 优化后整组封装的抽取、封装和解封恢复分别约 2.25、3.41、4.07 秒；解封后 RSS 检查点约 640 MiB，系统观测峰值约 803 MiB。整体密文需要同时保留全部原始、载体、方法对象、密文和恢复结果，宿主端尚可运行，但不适合作为移动端候选。
- 逐 DEX 顺序处理的总密文为 36205686 字节，仅比整组多 440 字节；抽取、封装和解封恢复分别约 2.24、3.40、4.04 秒，耗时基本不变。缓存后的系统观测峰值约 144 MiB，相对整组降低约 82%；RSS 检查点受测试进程和分配器状态影响，结论只比较数量级，不作为正式预算值。

资源评审结论：停止整体大密文方向。后续候选结构应采用“小型认证总索引 + 每个 DEX 独立认证密文”：总索引绑定稳定顺序、DEX 身份、载体摘要、每个密文摘要及 nonce；每个 DEX 使用同一主密钥派生出的独立子密钥或唯一 nonce 认证加密，可以顺序解封并及时释放临时数据。单 DEX 独立密文不能省略总索引，否则仍可能发生整份密文的缺失、替换或跨 APK 混用。

分层认证索引结果（2026-07-31）：

- 新增测试私有 `layered` 模块，只编排现有单 DEX `bundle`，不解析方法记录、不复制载荷编码规则，也不依赖文件系统、Stub 或 UI。
- 调用方为每个包提供安全随机的 96 位 nonce 基值；索引使用基值，各 DEX 分片按稳定顺序使用基值加计数器 1…N（模 `2^96`）。最多 256 个 DEX 的当前边界内包内 nonce 自动唯一，且不缩短跨包随机空间；解封仍会显式拒绝任何重复值。
- 认证总索引绑定版本、DEX 数量和顺序、每个 DEX 的稳定身份、占位载体 SHA-256、分片 nonce 及分片密文 SHA-256。总索引使用同一主密钥和独立 nonce 认证加密，并以独立协议标识作为附加认证数据。
- 解封先核对成员数量和 nonce 唯一性，再认证总索引并根据当前载体与分片重建索引逐字节比较。只有整组通过后才逐个调用单 DEX 解封器；恢复结果通过消费回调立即交付，分层模块不累计全部明文 DEX。
- 双 DEX 纯内存回归已覆盖正确顺序消费、分片缺失、分片错序、分片密文篡改、载体错序、索引密文篡改、重复 nonce，以及使用不同 nonce 基值生成的另一组分片替换，所有异常均在消费业务 DEX 前失败关闭。
- 已授权真实 12 DEX 样本进一步完成分层索引闭环，12 个分片全部按稳定顺序逐字节恢复。认证总索引密文为 1110 字节，逐 DEX 分片密文合计 36205686 字节；总索引额外成本约占分片密文 0.003%，没有改变上一阶段的体积结论。
- 当前以同一主密钥配合不同 nonce 保护索引和分片，并通过不同附加认证数据区分用途。正式设计可进一步使用 HKDF 按用途、DEX 身份和序号派生子密钥，但必须先证明额外密钥层次带来明确收益；本阶段不提前冻结。
- 包内唯一不等于跨包唯一。正式加固端必须为同一主密钥下的每次加固生成新的安全随机前缀，不得复用测试固定值；若未来需要确定性构建，应改用确定性派生且确保密钥/上下文唯一，不能直接固定 nonce。

至此首轮兼容样本、静态收益、认证清单、加密代码载荷、真实资源评估和分层认证索引均已完成。分层离线协议已经满足完整性门槛，离线格式不再继续扩展。

运行时恢复路径评审（2026-07-31）：

| 候选路径 | 可行性 | 结论 |
|----------|--------|------|
| 私有目录重建完整 DEX，再复用现有 `DexInjector` | 兼容现有 API 19 以上文件加载链路 | 会重新产生可提取的完整明文 DEX 文件，不能实现本专项的核心增益，停止 |
| 每个 DEX 顺序解封并交给单独类加载器 | 可以降低解封阶段临时峰值 | 多加载器会改变跨 DEX 查找顺序和类身份，不能作为通用 APK 方案，停止 |
| 重建全部完整 DEX 后使用 `InMemoryDexClassLoader` | API 26 起有公开单缓冲构造，API 27 起支持 DEX 缓冲数组 | Android 公开接口要求缓冲区包含完整 DEX 文件，最终仍需同时持有全部完整 DEX；分层密文只能降低解封临时峰值，不能消除完整 DEX 的长期内存成本，不进入正式实现 |
| `AppComponentFactory` 配合稳定代理加载器 | API 29 起可通过公开回调选择应用组件类加载器 | 只解决加载器身份和初始化时序，不提供方法代码片段的定义或回填能力；可继续服务完整内存 DEX 独立研究，不能解决本专项恢复问题 |
| 修改 ART 方法结构、运行时回填指令或系统函数 Hook | 技术上可能实现按方法恢复 | 依赖非 SDK 私有实现、Hook、可写可执行内存或自修改代码，违反既定安全与兼容边界，禁止 |
| 自定义解释器或方法虚拟化 | 不依赖系统提供按方法定义接口 | 属于独立虚拟机体系，兼容、性能、调试和安全软件风险都远超当前专项，不作为本轮延伸 |

评审依据：

- Android 官方 [`InMemoryDexClassLoader`](https://developer.android.com/reference/dalvik/system/InMemoryDexClassLoader) 契约明确要求 `ByteBuffer` 中包含完整 DEX 文件内容；公开接口没有接收方法代码片段或向已加载 DEX 回填 `code_item` 的能力。
- Android 官方 [`AppComponentFactory.instantiateClassLoader()`](https://developer.android.com/reference/android/app/AppComponentFactory#instantiateClassLoader(java.lang.ClassLoader,%20android.content.pm.ApplicationInfo)) 允许应用建立自定义类加载器层级，但不改变类加载器只能加载完整 DEX 的输入边界。
- Android 9 起限制通过反射或 JNI 访问[非 SDK 接口](https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces)；这些接口会随版本变化并可能直接被阻断，不能作为面向多 Android 版本和厂商系统的正式基础。
- 已完成的完整内存 DEX 实验已经证明公开类加载链路可行，同时也记录了真实大 APK 的长期内存门禁未通过。方法代码分离在加载前仍需还原同等规模的完整 DEX，不能用较小密文体积绕过该门禁。

最终决定：停止把当前方法代码分离协议接入正式 Stub、DEXB、APK、CLI 或 GUI。保留测试私有离线实现、真实样本数据和失败关闭用例，作为静态保护研究证据；只有 Android 将来提供稳定的片段级公开加载能力，或项目另行批准自定义虚拟机专项时才重新评审。该停止结论不是实现失败：离线协议已证明结构与代码分离的静态收益，但在当前安全、兼容和内存约束下没有满足产品要求的运行时落点。

### 当前明确不做

- 不发布预览版本，不生成面向用户的 APK。
- 不修改 DEXB v5、资源协议和版本号。
- 不增加 GUI、CLI 选项或配置字段。
- 不引入 Dobby、ByteHook 等 Hook 框架。
- 不实现运行时方法回填、分片恢复或方法虚拟化。
- 不将当前内存 DEX 候选提升为正式功能。

## 首轮原型范围

首个原型严格限制为：

- 单 DEX。
- 普通 Java 方法。
- 不包含动态生成 DEX、热修复框架和二次壳。
- 只验证方法清点、结构载体、代码载荷和离线往返恢复。
- 只通过测试或内部研究入口调用，不进入 GUI、CLI 和正式资源。

离线处理阶段不作 Android 系统版本兼容承诺；如果未来进入运行时原型，首轮才限定 API 31 以上。

首个原型必须完整保留原始 DEX，并逐项比较类、字段、方法、指令、异常表和运行结果；不能只以应用首页成功打开作为验收。

## 后续扩展顺序

原型通过后按以下顺序扩大，每一步都可独立停止：

1. 单 DEX Java：普通调用、继承、接口、异常和反射。
2. Kotlin：协程、合成方法、默认参数和内联相关结构。
3. 多 DEX：跨 DEX 引用、加载顺序和重复类处理。
4. 现有兼容样本：真实 Application、ARouter、Android 9 共享库和 JNI。
5. 性能与稳定性：冷启动、峰值内存、JIT/AOT、GC 后延迟类加载。
6. 分片恢复可行性：只在前五步全部达到门槛后开始。

Android 4.4～11 不随 API 31 以上原型自动获得支持。若未来向下扩展，必须重新评估 ART、启动期 Keystore 上下文和文件加载限制。

## 候选模块边界

不新增独立 crate，先在现有模块内形成可删除的私有研究边界：

| 单元 | 负责 | 不负责 |
|------|------|--------|
| `shield-core` DEX 转换模块 | 解析 DEX、生成稳定方法索引、结构载体和加密代码载荷 | Android 运行时恢复和类加载 |
| 载荷协议模块 | 定义版本、分片描述、摘要和错误语义 | 具体 GUI、文件缓存和 ART 操作 |
| Stub Native 恢复模块 | 认证代码载荷并在受控内存中重建需要的数据 | 解析 GUI 配置和 APK 重打包 |
| `DexInjector` | 注入最终可加载的内存 DEX | 理解方法索引、加密和分片协议 |
| GUI / CLI | 原型阶段不暴露；正式评审后只传固定保护级别 | 选择方法、修改协议或处理运行时内存 |

研究实现不得把 DEX 解析规则继续堆入现有 `process_dex()`，也不得让 `DexInjector` 同时承担解密、重建和注入三种职责。

## 协议与兼容策略

DEXB v5 当前表示完整 DEX 集合，旧 Stub 只支持 v5。结构与代码分离会改变载荷语义，因此必须：

- 使用新的协议版本或独立能力字段，不能把新布局伪装成 v5。
- 新 Stub 遇到未知版本时失败关闭。
- 旧 Stub 不会被新加固端静默配对。
- 标准资源和 Android 4.4 资源不要求同时支持实验协议；不支持时核心必须在加固前拒绝。
- 原型产物不得用于覆盖安装或对外稳定发布。

具体二进制布局只有在原型确认所需字段后再冻结，本文不提前规定偏移和长度。

## 验收指标

### 功能正确性

- 原型样本的全部方法行为与原 APK 一致。
- 结构载体不能被常规 DEX 工具直接还原为完整业务实现。
- 代码载荷缺失、篡改、错序或版本不匹配时失败关闭。
- 进程中不产生持久完整业务 DEX 文件。

### 安全效果

- 分别记录仅提取结构载体、仅提取代码载荷和单次内存快照能够恢复的代码比例。
- 评估是否存在稳定的自动合并路径；如果只是修复 header 即可恢复，则原型失败。
- 不使用“无法脱壳”作为结论，只描述相对于完整 DEX 加密增加了哪些必要步骤。

### 安全软件门禁

离线原型不改变正式 APK，因此本阶段只建立后续扫描口径，不上传用户提供的样本：

1. 选用自有合成 APK 和许可明确的公开测试 APK，保存来源、版本和哈希。
2. 原始、现有正式加固和候选加固使用同一签名证书，避免把签名信誉差异误判为实现差异。
3. 记录每个检测引擎、检测名称、首次出现版本和相对基线增量，不只记录“多少家报毒”。
4. 分别测试新增能力，禁止一次叠加方法抽离、Root 严格模式和新的反调试行为后再定位。
5. 出现主流手机厂商安全检测拦截、应用市场拒绝或多家主流引擎新增同类检测时，停止集成并定位最小触发行为。
6. 不通过加密检测代码、随机变形或隐藏 Hook 解决门禁失败；无法移除风险行为时终止该运行时方案。

### 性能门槛

- 与完整内存 DEX 路径对比冷启动耗时和峰值内存。
- 记录不同 DEX 大小和方法数量的增长曲线。
- 出现不可控的双份完整内存、长时间主线程阻塞或频繁崩溃时停止扩大范围。

### 兼容门槛

- 离线原型只对所覆盖的 DEX 格式和样本结论负责，不代表任何 Android 运行时版本已经兼容。
- 未来首个运行时原型只对 API 31 以上结论负责。
- 扩展阶段必须逐项通过 Kotlin、多 DEX、反射、JNI、ARouter 和 Android 9 样本。
- 未通过的能力必须显式标记，不允许静默回退为保护强度不同的路径。

## 停止条件

出现以下任一情况，应保留研究报告并停止进入生产：

- 只需机械修复少量头字段即可恢复完整 DEX。
- ART 或厂商系统差异导致无法建立可维护的稳定边界。
- 冷启动、内存或崩溃率成本明显高于保护收益。
- 为兼容常见框架必须长期维护大量系统版本私有 Hook。
- 运行时恢复必须依赖系统/ART Hook、可写可执行代码页或 Native 自修改代码。
- 相对同签名基线出现无法通过删除风险行为解决的稳定安全软件检出增量。
- 安全效果无法通过可复现实验与现有完整内存 DEX 路径区分。

## 路线定位

如果离线研究最终获准进入运行时，运行时能力的依赖顺序固定为：

```text
完整 DEX 文件加载
  → 完整 DEX 内存加载
  → 结构与方法代码分离后内存重建
  → 分片恢复
  → 按需方法恢复可行性
  → 少量关键方法虚拟化调研
```

方法清点、离线抽取、逐字节恢复，Java、R8、反射、Kotlin、多 DEX、ARouter 与 JNI 真机语义，以及仓库样本和真实多 DEX 样本的静态收益评估已经完成。离线方向可以继续设计认证的整组载荷清单；运行时仍须先提出不依赖私有 Hook、高风险内存权限或自修改代码的恢复路径。该专项研究不等待内存 DEX 正式发布，也不预占具体版本号。离线原型只能证明处理器正确性和静态保护收益，不能自动获得运行时实施资格。每一层都必须有独立原型、报告、安全软件门禁和停止条件，不能一次性组合实现。
