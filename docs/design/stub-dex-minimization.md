# Stub DEX 最小化与分阶段加载可选演进

本文定义壳启动 DEX 的后续精简方向，并评估“将更多壳逻辑加密保存、运行时再加载”的可行边界。该能力属于后续可选演进，不是当前稳定版本的发布前置条件，也不代表已经实现。

## 背景与现状

当前标准资源中的 `stub-classes.dex` 为 18,300 字节，静态结构包含 7 个类、177 个方法、16 个字段和 319 个字符串。完整机器可读快照见 [Stub DEX 基线报告](stub-dex-baseline.json)。体积本身并不大，主要问题是所有兼容逻辑都进入同一份启动 DEX，使静态分析者能够一次看到：

- Application 启动与真实 Application 替换流程；
- DEX 解密、缓存与注入的 Java 调用边界；
- ARouter 路由缓存兼容逻辑；
- Android 9 共享库兼容逻辑；
- 低版本 ART/Dalvik 反射路径及诊断字符串。

继续压缩几 KiB 对安装包收益有限。本项工作的核心是减少默认产物不需要的类、方法和可读行为线索，同时保持已验证的系统兼容性。

## 目标

- 根据输入 APK 的实际能力选择最小 Stub，而不是始终注入完整功能集合。
- 降低启动 DEX 中可见的类、方法、合成类和诊断字符串数量。
- 保持业务 DEX 最终注入应用原有 `PathClassLoader`，不破坏类身份和框架兼容性。
- 标准模式、Android 4.4 工控兼容模式、ARouter、Android 9 共享库与 Native 库打包均可独立组合验证。
- 用构建指标、启动性能和设备矩阵决定是否继续，不以“常规工具不易阅读”作为唯一结论。

## 非目标

- 不追求“初始 DEX 中没有 Java 代码”。Manifest 声明的 Application 必须位于系统最先加载的 DEX 中。
- 不承诺隐藏加固事实或阻止已控制进程、Root/内核环境的攻击者分析。
- 不在正式路径中运行时生成 DEX 字节码。
- 不把全部 Java 逻辑机械迁移到 Native，也不直接依赖未公开的 ART/Dalvik 内部结构。
- 不修改业务 DEX 加密格式 DEXB v5；二阶段 Stub 如需独立载荷，必须使用独立协议和能力字段。

## 启动边界

Android 必须先从 APK 的初始 `classes.dex` 创建并调用 Manifest Application，随后 Java 才能执行 `System.loadLibrary()` 进入 Native。因此至少需要保留：

```text
最小 Application 入口
  → 加载任务别名 Native 库
  → 读取并校验运行配置
  → 建立业务 DEX 加载路径
  → 启动真实 Application
```

将全部壳代码藏入 SO 会遇到启动悖论：在 Java 入口存在之前，SO 没有可靠的系统调用点。可优化的是初始 DEX 的职责和暴露面，而不是消除初始 DEX。

## 推荐主路线：按能力选择有限 Stub 变体

### 能力维度

加固端已经能够从输入 APK 或任务选项确定以下信息：

| 能力维度 | 识别来源 | 对 Stub 的影响 |
|----------|----------|---------------|
| 运行基线 | GUI/核心选择的标准或 Android 4.4 工控兼容资源 | 是否包含 API 19～20 Dalvik 路径 |
| ARouter | 现有路由表扫描结果 | 是否包含路由缓存准备逻辑 |
| 系统共享库 | Manifest `uses-library` 与 DEX 预检 | 是否包含 Android 9 共享库兼容逻辑 |

首期只允许这三个有限维度，理论上最多形成 `2 × 2 × 2 = 8` 个预构建变体。不得把每个框架或系统版本继续扩展成独立维度，避免资源矩阵失控。

### 变体职责

每个变体均保留共同启动核心：

- 最小 Application 生命周期；
- Native 加载、环境检查和解密入口；
- 当前运行基线所需的 DEX 注入；
- 真实 Application 替换；
- 必要的失败关闭逻辑。

ARouter 和系统共享库逻辑只进入声明相应能力的变体。Android 4.4 工控兼容变体额外包含 Dalvik 路径；标准变体仍需保留 API 21～23 已验证的 ART Element 注入，不能误缩减为只支持高版本。

### 资源协议

`resources.zip` 与 `resources-api19.zip` 后续增加类型化的变体清单，例如：

```json
{
  "stub_variant_protocol": 1,
  "variants": {
    "base": { "dex": "stub/variants/base/classes.dex", "sha256": "..." },
    "arouter": { "dex": "stub/variants/arouter/classes.dex", "sha256": "..." },
    "shared_library": { "dex": "stub/variants/shared-library/classes.dex", "sha256": "..." },
    "arouter_shared_library": { "dex": "stub/variants/arouter-shared-library/classes.dex", "sha256": "..." }
  }
}
```

标准和 Android 4.4 资源分别维护自己的清单，但使用相同协议语义。核心根据预检结果构造固定能力键，校验路径、摘要和协议后选择 DEX。所需变体缺失、摘要不符或出现未知能力时必须在解包前失败，不允许静默使用完整变体掩盖资源错配。

首期可以保留一个仅供构建回归的完整变体，但正式加固不得把它作为失败回退。

## 启动 DEX 静态精简

在引入变体前先进行不改变运行语义的清理：

1. 将非必要 Lambda 改为普通循环或显式静态实现，减少 R8 生成的合成类。
2. 审计 Release 诊断字符串，用户不可消费的路径名称改成稳定短错误码；详细原因只保留在内部测试映射中。
3. 删除重复适配层和仅供调试的集合转换，保持 JNI 回调边界明确。
4. 为 DEX 大小、类数、方法数、字段数和字符串数生成构建报告，并设置只防止意外膨胀的上限。

JNI Native 回调涉及的 Java 类仍必须使用 `{ *; }` 完整保留。不得为了减少方法数量削弱 ProGuard 保留规则，否则 R8 无法感知的 Native 回调会在运行时缺失。

缓存目录和文件名属于已有运行协议，首轮不为追求短字符串改名。未来如调整，必须独立设计覆盖安装与旧缓存失效策略。

## Java 与 Native 的职责调整

适合逐步下沉到 Native 的逻辑：

- 缓存文件摘要、认证、原子写入和规范路径校验；
- 签名摘要与载荷认证；
- 解密、解压和与文件描述符直接关联的操作；
- 已有稳定公开接口支撑的高版本加载辅助。

继续保留在 Java 的逻辑：

- Manifest Application 生命周期与真实 Application 交接；
- API 19～23 的 Dalvik/ART 反射兼容路径；
- ARouter 初始化前缓存准备；
- Android 9 系统共享库 ClassLoader 兼容。

职责下沉必须以减少跨语言往返或复用安全边界为依据，不能只为隐藏字符串把稳定的 Java 兼容代码改写成依赖系统私有结构的 Native Hook。

## 可选实验：加密二阶段 Stub DEX

### 候选流程

```text
初始最小 Stub DEX
  → 加载 Native
  → 认证并解密二阶段 Stub DEX
  → API 29+ 内存加载二阶段编排代码
  → 业务 DEX 仍注入应用 PathClassLoader
  → 启动真实 Application
```

二阶段 Loader 只承载壳编排逻辑，不得成为业务类的 defining loader。否则 ARouter、反射、JNI、组件实例化和跨 DEX 类型判断可能因双 ClassLoader 产生新的兼容问题。

### 载荷位置取舍

| 方案 | 收益 | 问题 | 结论 |
|------|------|------|------|
| 每个 ABI 的 SO 内嵌同一密文 DEX | 容器表面上更分散 | 四 ABI 重复占用空间；密钥和解密逻辑仍在客户端；资源选择复杂 | 不作为默认设计 |
| 在启动 DEX 尾部或独立资源中保存单份认证密文 | 只保存一份，协议和摘要易统一 | 仍可识别为载荷；必须设计边界和版本 | 实验首选 |
| 运行时动态生成 DEX | 静态文件中没有完整二阶段 DEX | 字节码生成、校验和异常表维护成本高，兼容和安全收益缺乏证据 | 不采用 |

如果后续实验必须比较 SO 内嵌方案，也只能生成每个 ABI 一致的认证载荷，并记录安装包增量；不能把 SO 当作密钥保险箱或宣称因此无法提取。

### 实验范围

- 仅 API 29 以上，与既有内存 DEX 实验共同验证。
- 默认关闭，不进入正式 GUI，不进入对外正式资源。
- API 19～28 继续使用单阶段文件路径；不得为二阶段 Stub 新增另一份落盘明文 DEX。
- 不与缓存安全、Root 策略、Native 库别名或 DEX 结构分离在同一实现提交中开发。

采用 API 29 而不是 API 26 作为首个范围，是为了沿用已有内存 DEX 生产候选边界，减少多 DEX 构造、厂商实现和 Android 9 共享库兼容变量。实验未达门槛时直接保留报告并删除或关闭路径，不阻塞正式版本。

## 实施阶段

### 建立基线与构建守门

- 构建后输出每个变体的字节数、类数、方法数、字段数和字符串数。
- 保存当前完整 Stub 的基线报告，识别合成类和主要字符串来源。
- CI 只在 Stub/资源相关变更或手动完整验证时检查指标，不因普通文档或 GUI 文案变化构建全部变体。

当前基线工具已经落地为 `scripts/analyze_stub_dex.py`，可直接读取 `stub-classes.dex` 或资源 ZIP，不依赖 Android SDK 的分析命令。维护者本地执行：

```bash
make build-stub
make audit-stub-dex
```

报告输出到 `shield-stub/build/outputs/resources/stub-dex-metrics.json`。当前守门上限为 20,000 字节、8 个类、190 个方法、20 个字段和 340 个字符串；阈值只用于阻止无意膨胀，不代表精简目标。手动完整 CI 在壳构建后执行同一检查，普通文档和 GUI 变更不会因此触发壳构建。

基线暴露的主要可读线索集中在缓存错误、ARouter、Dalvik/ART 路由、Android 9 共享库准备及 Application 替换失败信息。下一阶段应先区分用户可消费错误和仅供内部定位的诊断信息，再做无语义变化清理；不得仅为减少字符串数量删除失败关闭所需的分支。

### 完成无语义变化精简

- 清理合成类和无消费入口的诊断字符串。
- 对比混淆映射、JNI 注册、DEX 校验和及启动性能。
- 先使用现有完整功能 DEX 完成设备回归，不在同一阶段引入变体选择。

### 引入有限变体与能力选择

- 构建标准/兼容两组有限变体和清单。
- 核心实现类型化能力键、摘要验证和失败关闭选择。
- 使用无设备端到端测试断言最终 APK 只包含所需能力。
- 设备矩阵通过后，才考虑把最小变体用于正式资源。

### 评估二阶段加载实验

- 等 API 29 以上完整业务 DEX 内存加载取得稳定证据后再启动。
- 先比较单份密文载荷与 SO 内嵌方案的大小、启动耗时和可提取面。
- 只保留能够证明额外收益且未引入第二业务 ClassLoader 的实现。

## 测试矩阵

### 自动验证

- 能力识别：基础、仅 ARouter、仅共享库、两者同时存在。
- 资源选择：标准/Android 4.4 工控兼容模式与所有能力组合均选择唯一变体。
- 契约检查：变体摘要、协议、必需类和 JNI 回调方法完整；非目标扩展类不存在。
- 失败路径：未知能力、清单缺失、摘要不符和变体缺失均不生成输出 APK。
- 打包兼容：Native 任务别名、`extractNativeLibs=false`、四 ABI 和 16 KB 对齐不回归。

### 设备验证

| 环境 | 重点 |
|------|------|
| API 19 | Dalvik、双 DEX、真实 Application、首次启动、缓存命中与覆盖安装 |
| API 21 / 23 | ART Element 注入、ARouter 与业务 Native 库 |
| API 28 | 系统共享库优先级、ARouter 与 Native 库组合 |
| API 29+ | 单阶段基线；实验开启时验证二阶段内存加载与延迟类加载 |
| API 35 16 KB / API 36 | Native 直接映射、冷启动、缓存命中、覆盖安装与完整能力组合 |

每个关键样本都必须至少覆盖首次安装、清除数据后首次启动、缓存命中和同签名覆盖安装。不能只以首页打开作为结论。

## 量化门槛与停止条件

主路线首轮以当前完整 Stub 为基线：

- 基础变体的方法数和字符串数目标至少下降 20%，实际阈值在基线工具产出后冻结。
- 冷启动中位数不得回退超过 5%，内存峰值不得出现新的长期双份持有。
- 任一已支持系统、ARouter、共享库、签名或 Native 打包路径回归时，不进入正式资源。

二阶段实验只有同时满足以下条件才进入后续评审：

- 初始可见 Stub DEX 的方法数和字符串数相对完整 Stub 至少下降 40%。
- API 29 以上冷启动中位数回退不超过 10%，且没有新增持久明文 Stub DEX。
- 多 DEX、真实 Application、ARouter、Android 9 共享库、Native 库、GC 后延迟类加载与 16 KB 回归全部通过。
- 与单阶段最小变体相比，提取实验能够说明新增的必要分析步骤，而不只是改变文件位置。

出现以下任一情况应停止二阶段方案：

- 需要第二个业务 ClassLoader 才能工作；
- 必须在 API 29 以上重新落盘完整二阶段 DEX；
- 四 ABI 载荷复制显著增加包体，且无法证明相应收益；
- 仅通过定位解密函数即可稳定得到与原完整 Stub 等价的单一载荷；
- 厂商兼容、启动耗时或维护成本高于静态暴露面降低的收益。

## 路线与版本边界

推荐依赖顺序为：

```text
构建指标与静态清理
  → 有限 Stub 变体
  → API 29+ 完整业务 DEX 内存加载稳定
  → 加密二阶段 Stub DEX 独立实验
  → 再评估 DEX 结构与方法代码分离
```

构建指标、静态清理和有限变体可以作为独立安全治理任务实施，不绑定当前 `1.2.7`，也不阻塞缓存安全与环境策略正式版。二阶段 Stub DEX 不预占版本号，只能在 API 29 以上内存加载稳定后作为可删除实验推进。

本方案与 [Android 运行时安全与 DEX 缓存演进设计](runtime-security.md)、[DEX 结构与方法代码分离研究](dex-code-separation.md) 和 [Native 库名称去品牌化与按任务别名设计](native-library-alias.md) 分别解决不同问题，实施时必须保持独立提交、独立开关和独立回归结论。
