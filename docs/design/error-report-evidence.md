# 错误报告可诊断性补齐

## 背景与版本

2026-10-13 检查真实主动报告，只有 apktool、退出码 1 和粗粒度重打包类别；Java、工具版本均空，无法区分资源编译、资源链接、XML、文件访问与编码问题。非官方版本上报不能作为官方缺陷证明，但暴露了现有协议证据不足。

维护者已批准纳入 1.4.2：保留已公开的 `1.4.2-rc.1`，完整实施与验证后交付 `1.4.2-rc.2`，不移动旧标签，不直接跳过候选发布为正式版。

## 架构与安全决策

这是已获批准的跨端报告协议演进：核心仅从工具输出生成有限证据，不保留原始字节；GUI 负责任务步骤、路径特征和环境快照；Worker 负责严格校验、兼容与存储。无新依赖、无数据库表变更，不扩张匿名统计。证据和环境只进逐份确认的报告。

第二版采用 `schema_version=2`、`sanitizer_version=2`，分类计数仍为第一版。服务端同时接受第一版，旧版证据仍须为空。新报告在已有 `payload_json` 中保存扩展字段，原有索引列不变，沿用 8 KiB 上限、幂等、限流、30 天保留及私有查询。

错误摘要不采用“正则替换后上传任意原文”：按具体工具识别资源缺失、属性缺失、重复资源、资源编译/链接、XML 解析、内存不足、Java 字节码版本、ZIP、文件权限/磁盘等特征，只输出固定模板及标准异常类别。路径、资源名、包名、属性自定义名等变量完全舍弃。最多八条，未知内容明确标为未识别；摘要不是原始日志，也不承诺覆盖所有错误。

第二版报告的 `details` 保存：

- `execution_step`：精确任务步骤枚举，区分 `modify_manifest` 与 `repack`；既有统计 `stage=manifest` 为兼容保留，不冒充精确步骤。
- `input_path`、`output_path`：仅布尔特征（非 ASCII、空格、特殊字符、超过 240 个 UTF-16 单元），无真实路径、长度数值或哈希；证书任务缺少任务输入时为 null。
- `java_version`、`os_version`：所选 JVM 报告的数字版本；厂商仅允许固定枚举，无法安全取得为 null。系统版本是 JVM 的 `os.version`，不是对原生系统补丁级别的完整探测。
- `evidence_status`：已识别或无可用证据；`evidence` 为固定摘要模板，不透传错误文本。

Java 与实际调用的工具版本采用失败后的有界离线探测，不联网，不改环境，不记录完整属性或路径；后台完成后一次冻结报告，再展示。未能可靠关联实际工具路径时版本为空，不用内置工具版本冒充自定义工具版本。超时或探测失败不改变原任务结果。

## 验收与停止条件

相同退出码 1 的资源缺失、XML 解析、内存不足应生成不同摘要；敏感路径、Alias、密码、DN、包名、URL、环境变量和异常自定义文本均不能进入报告。摘要无法安全取得时仅空证据，不回退上传整段错误。

自动化不能替代原生 Windows 中文路径和真实桌面交互验收。旧版报告的空字段不可回填为推测值；非官方客户端字段也不作为可信构建证明。线上只使用明确标记的维护者安全样本验证，不展示用户应用材料。
