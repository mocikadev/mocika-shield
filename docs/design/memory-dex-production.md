# API 31 以上内存 DEX 正式接入设计

## 目标与结论

本文把已经通过隔离探针验证的替换 ClassLoader、原组件工厂委托和认证崩溃回退，收敛为正式 Stub 的候选接入方案。

推荐采用“独立候选资源包、显式选择、默认关闭”的渐进方案：现有标准资源和 Android 4.4 资源保持原协议与文件加载行为；新增内存候选资源只供内部回归使用。完整门槛通过前不进入 GUI、不成为自动选择项，也不对用户承诺。

这项能力解决 API 31 以上设备在正常启动后长期保存完整明文业务 DEX 的问题。API 28～30 保留原组件工厂语义但固定使用认证文件缓存；其中 [Android 10](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-10.0.0_r1/keystore/java/android/security/KeyStore.java) 和 [Android 11](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-11.0.0_r1/keystore/java/android/security/KeyStore.java) 的 Keystore 在 Application 附加阶段仍依赖尚未建立的全局 Application，[Android 12](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-12.0.0_r1/keystore/java/android/security/KeyStore.java) 已移除这项依赖。为避免提前篡改框架 Application 引用或降低状态认证强度，内存边界提升到 API 31。它不能阻止 Root、进程注入或运行时内存转储，也不改变 DEXB v5 加密格式。

## 已有证据

隔离探针已经验证：

- API 29、API 35 16 KB、API 36 的双 DEX、五类组件、Native 库和回收后延迟加载。
- 正式 DEXB v5 签名绑定解密与异签名失败关闭。
- AndroidX、自定义和未声明原 `AppComponentFactory` 的委托，以及递归配置拒绝。
- 真实 ARouter 样本首次安装、清除数据和同签名覆盖安装。
- Instrumentation、安装时动态特性、主进程和远程进程。
- 内存启动崩溃后的下一进程文件回退、粘性回退、连续失败关闭。
- 状态篡改、包装材料缺失、包装密文损坏和双进程并发首次启动。

这些结论只证明候选结构可行。探针中的类、文件名和 `SharedPreferences` 实现不直接复制到正式资源。

## 非目标

- 不支持 API 28 及以下使用内存 DEX；这些系统继续使用认证文件缓存。
- 不在同一进程内从内存加载器切换到文件加载器。
- 不修改 DEXB v5，不同时推进 DEX 结构与方法代码分离。
- 不把动态特性代码可加载描述为代码 split 已加密。
- 不增加 GUI 开关、公开 CLI 模式或自动推荐逻辑。
- 不承诺 Root 环境下无法提取业务代码。

## 资源与协议

### 资源产物

| 资源 | 行为 | 对外状态 |
|------|------|----------|
| `resources.zip` | API 21 以上标准文件加载 | 保持正式默认 |
| `resources-api19.zip` | Android 4.4 工控兼容文件加载 | 保持现有可选项 |
| `resources-memory.zip` | API 31 以上内存候选，API 30 以下认证文件加载 | 仅内部回归 |

候选资源通过现有隐藏 `--resources` 参数显式传入，不新增公开模式参数。自动资源查找永远只返回标准资源，避免候选能力被意外启用。

### 能力元数据

候选资源升级到独立的 Runtime 协议，至少声明：

```json
{
  "runtime_protocol": 3,
  "cache_schema": 1,
  "memory_dex": true,
  "memory_dex_min_api": 31,
  "stub_application": "混淆后的壳 Application",
  "stub_component_factory": "混淆后的壳组件工厂"
}
```

标准和工控资源继续使用 Runtime 协议 2、`memory_dex: false`。缓存协议不因内存候选而升级；文件回退必须复用现有 `DexCache` 的身份摘要、只读文件、目录级原子替换和异常重建。

核心只在显式提供候选资源时接受协议 3，并同时校验全部内存能力字段。字段缺失、版本不匹配、工厂类名无效或候选资源与 Manifest 注入能力不一致时，在创建输出 APK 前拒绝任务。

## 正式 Stub 边界

正式实现按职责划分为以下最小单元：

| 单元 | 负责 | 不负责 |
|------|------|--------|
| `StubApp` | 启动编排、环境检查、创建真实 Application、替换 Application 引用 | 状态持久化和具体加载器构造 |
| 壳组件工厂 | 向系统提供身份稳定的代理加载器，并委托原组件工厂 | 解密、回退决策和缓存重建 |
| 进程运行时协调器 | 当前进程的一次性初始化、原工厂实例和业务加载器状态 | 跨进程共享可变状态 |
| 内存载荷加载器 | 调用正式 Native 解密并创建唯一业务 `InMemoryDexClassLoader` | 崩溃判定和文件缓存 |
| 回退状态存储 | 每进程合法状态转换、HMAC 认证和 Keystore 密钥包装 | DEX 解密和加载 |
| `DexCache` | API 28 以下及回退路径的认证文件缓存 | 内存加载器生命周期 |

上述单元保持在现有 `shield-stub` 模块和 loader package 内，不新建 Gradle 模块。状态规则具有独立生命周期，应从 `StubApp` 拆出；固定的 Android 存储与 Keystore 实现不预先抽象成多套接口。

## 启动与回退流程

### API 31 以上

1. 系统创建壳组件工厂，工厂返回尚未初始化的稳定代理加载器。
2. `StubApp.attachBaseContext()` 执行隐藏 API 兼容与每次启动环境检查。
3. 协调器读取“载荷身份 + 进程身份”对应的认证状态，先同步写入本次待确认状态。
4. 内存模式复用现有 `Ld`/Native DEXB v5 解密，创建真实 `InMemoryDexClassLoader` 并一次挂接代理。
5. 文件回退模式调用正式 `DexCache.load()`，再使用现有文件注入路径；不得复制探针的临时文件实现。
6. 业务类开始定义后禁止切换模式。真实 Application 完成 `onCreate()` 后才异步写入成功状态。

### API 30 及以下

壳组件工厂不得触发内存解密。API 28～30 由壳工厂保持原组件工厂语义，再执行现有环境检查、`DexCache.load()` 和 `DexInjector.inject()`；API 27 以下不会创建壳组件工厂。候选 APK 在低版本系统上的行为必须与标准资源一致，Android 4.4 仍只使用专用工控资源，不使用内存候选资源。

### 状态转换

```text
新载荷或 memory_ready → memory_pending → memory_ready
memory_pending         → file_pending   → file_fallback
file_fallback          → file_pending   → file_fallback
file_pending           → 失败关闭
```

同一载荷发生一次未确认的内存启动后保持文件模式，不按时间自动重试。只有载荷身份变化、应用数据被用户清除或重新安装时才重新尝试内存模式，避免兼容性崩溃循环。

## 状态存储与安全边界

- 状态放入 `noBackupFilesDir`，不使用可被系统备份恢复的普通偏好文件。
- 文件名使用进程名摘要，记录正文同时包含协议版本、载荷身份、完整进程身份和状态。
- 每个进程使用独立随机 HMAC 密钥；密钥由独立 Android Keystore AES-GCM 密钥包装。
- 待确认状态必须同步、原子持久化；成功状态可以异步，丢失时只会保守回退。
- 记录缺失且没有历史状态时可以生成新密钥；记录存在但包装材料、Keystore 条目或 MAC 异常时必须失败关闭。
- Root 攻击者删除全部应用数据后等同于用户清除数据，无法依靠本状态机建立不可绕过的可信根。

## Manifest 与原应用语义

核心处理候选资源时必须：

- 保存原 `Application` 和原 `appComponentFactory`，分别使用独立元数据字段。
- 将壳 `Application` 与壳组件工厂写入 Manifest。
- 区分原应用未声明工厂、AndroidX 工厂、自定义工厂和递归指向壳工厂。
- 原工厂类不存在、类型不匹配、构造失败或递归配置时失败关闭。
- 保持 `extractNativeLibs`、Provider 初始化顺序、ARouter 路由清单、环境策略和任务级 Native 别名现有语义。

标准资源不写入壳组件工厂，避免内存候选改变当前正式 APK 的 Manifest 和启动路径。

## 兼容、迁移与回滚

- 标准资源升级到候选资源：旧认证文件缓存可以保留，但内存路径不读取其中的明文 DEX；发生回退时由 `DexCache` 校验后复用或重建。
- 候选资源回到标准资源：使用同一原始 APK 和签名重新加固覆盖安装；标准 Stub 忽略候选状态目录，并按现有缓存身份校验加载。
- 相同 `versionCode` 的不同 APK 继续以缓存根摘要区分，不能继承旧载荷状态。
- 进程名变化会生成新的进程状态；旧状态只作为可清理孤儿文件，不参与新进程判断。
- 版本降级不迁移或解释更高版本状态协议；标准资源完全忽略候选状态。
- 任何候选缺陷都可通过停止生成 `resources-memory.zip` 回滚，不需要修改 DEXB v5 或用户配置数据库。

## 分阶段实施

### 资源契约与构建隔离

- 核心解析协议 3，并验证候选资源字段；默认资源发现保持不变。
- 增加 Manifest 原组件工厂保存和候选工厂注入的结构测试。
- 在真实壳组件工厂进入 Stub 前不生成 `resources-memory.zip`，避免留下协议有效但运行入口不存在的误用产物。

完成条件：合成候选资源可以通过隐藏的显式资源路径完成协议选择和 Manifest 转换；自动资源发现拒绝候选能力；标准、工控资源和构建脚本保持不变。

### 正式运行时最小接入

- 已增加真实组件工厂、稳定代理和高版本类型隔离桥；构建脚本生成仅供显式路径使用的 `resources-memory.zip`。
- 已接入正式 Native DEXB v5 解密和唯一 `InMemoryDexClassLoader`，并把原组件工厂的五类组件创建语义交还委托对象。
- 已增加每进程协调器和认证回退状态存储：纯状态机不依赖 Android 存储，状态文件使用 `noBackupFilesDir` 原子替换，HMAC 原始密钥由每进程 Android Keystore AES-GCM 密钥包装。
- 文件模式复用正式 `DexCache` 和现有 DEX 注入器，不维护第二套明文缓存；一次未确认的内存启动后保持文件模式，文件启动再次未确认时失败关闭。
- API 28 以下固定走现有文件路径。

当前证据：API 28、API 29、API 30 ARM64 模拟器已通过认证文件路径、双 DEX、原组件工厂五类回调和主/远程进程，且未创建内存状态文件。API 31 ARM64 模拟器、API 33 Classin BH55A 真机与 API 35 OnePlus 真机已通过同签名 DEXB v5、双 DEX、原组件工厂五类回调和主/远程进程，两个进程分别生成认证状态，正常内存路径的应用私有目录没有生成明文 `.dex`。API 33 与 API 35 真机还通过了清除数据、标准/候选双向覆盖、真实 Application 异常后的文件回退及粘性重启、文件连续失败关闭、进程状态隔离、状态 MAC 损坏、包装密文损坏和 Keystore 条目删除；Classin 自动重试启动事务，OnePlus 等待显式重启，两种行为均形成预期状态转换。标准资源和 Android 4.4 资源仍沿用协议 2，候选能力未进入 GUI。

完成条件：API 30 文件路径、API 31 最低内存边界和两家不同厂商的 API 31 以上真机均已通过。候选能力仍不进入 GUI。

### 完整生产门禁

- API 28～30 文件路径、API 31 最低内存边界、API 35 16 KB、API 36，并至少补充一台不同厂商 API 31 以上真机。
- 真实 ARouter、AndroidX/自定义组件工厂、多 DEX、Native、Instrumentation、主/远程进程。
- 首次安装、清除数据、双向覆盖迁移、内存崩溃、文件失败、状态和密钥异常。
- Root 兼容/严格策略、冷启动中位数、即时与整理后 PSS、私有目录 DEX 暴露检查。
- 动态特性继续明确标记为明文阻塞项；未完成代码 split 保护前不宣称 AAB 全面保护。

完成条件：没有高优先级兼容缺陷，性能和内存代价在发布说明中可解释，回滚路径真实验证通过，才能进入 Alpha 集成版本。

### 性能门禁结果

性能脚本对同一双 DEX 测试载荷分别生成同签名标准资源和内存候选 APK。每种形态先完成一次初始化，再强制停止应用并采集 7 次稳态冷启动；同一设备按“标准优先”和“内存优先”各执行一轮，合并 14 个样本取中位数。PSS 为主进程与远程进程的系统 `TOTAL PSS` 之和，整理后数据在统一发送内存整理信号并等待两秒后采集。

| 设备 | 形态 | 冷启动中位数 | 即时双进程 PSS 中位数 | 整理后双进程 PSS 中位数 |
|------|------|--------------|-------------------------|---------------------------|
| Classin BH55A / API 33 | 标准文件 | 341.5 ms | 47331.5 KB | 47345 KB |
| Classin BH55A / API 33 | 内存候选 | 383 ms（+12.2%） | 48319.5 KB | 47869.5 KB（+524.5 KB） |
| OnePlus 5 / API 35 | 标准文件 | 463.5 ms | 42075 KB | 46324.5 KB |
| OnePlus 5 / API 35 | 内存候选 | 502.5 ms（+8.4%） | 43632 KB | 48139.5 KB（+1815 KB） |

整理后 PSS 增量在当前小型双 DEX 载荷上为约 0.5～1.8 MB，没有出现长期双份完整 DEX 的量级。冷启动以每台设备相对标准资源不回退超过 10% 作为当前候选参考线：OnePlus 通过，Classin 回退 12.2%，因此性能门禁尚未全面通过。该结果不外推到真实大型应用；候选资源继续默认关闭且不进入 GUI，下一阶段先对读取、Native 解密、直接缓冲区构造、加载器创建和组件初始化做分段剖析，再决定局部优化或接受范围。

### 真实大型 APK 补充验证

补充样本为 329 MB、12 个 DEX、DEX 明文总量约 113 MB 的真实应用。标准资源和内存候选均从同一重签输入加固，并使用同一测试证书签名；API 33 与 API 35 真机均完成标准/候选覆盖安装。两类场景分开采样，每种形态各 3 次：

- 首次启动：每轮安装后清除应用数据，覆盖解密、状态创建和应用初始化的完整成本。
- 日常冷启动：先清除数据并启动一次完成初始化，随后只强制停止应用，不再清除数据。

| 场景 | 设备 | 形态 | 启动中位数 | 启动 15 秒后 PSS 中位数 |
|------|------|------|--------------|--------------------------|
| 首次启动 | Classin BH55A / API 33 | 标准文件 | 3432 ms | 298227 KB |
| 首次启动 | Classin BH55A / API 33 | 内存候选 | 2802 ms（-18.4%） | 289046 KB（-3.1%） |
| 首次启动 | OnePlus 5 / API 35 | 标准文件 | 不采信 | 299798 KB |
| 首次启动 | OnePlus 5 / API 35 | 内存候选 | 不采信 | 238714 KB（-20.4%） |
| 日常冷启动 | Classin BH55A / API 33 | 标准文件 | 1561 ms | 169822 KB |
| 日常冷启动 | Classin BH55A / API 33 | 内存候选 | 1681 ms（+7.7%） | 171885 KB（+1.2%） |
| 日常冷启动 | OnePlus 5 / API 35 | 标准文件 | 不采信 | 154998 KB |
| 日常冷启动 | OnePlus 5 / API 35 | 内存候选 | 不采信 | 260728 KB（+68.2%） |

全部 12 次首次启动和 12 次日常冷启动均保持主进程存活，未出现致命异常。OnePlus 系统在部分轮次不返回 `TotalTime`，并把 `WaitTime` 固定在约 3 秒，因此不使用该设备的启动耗时推导性能结论。其内存候选日常 PSS 三次为 229550 KB、260728 KB 和 378251 KB，波动和中位数增量都明显；这组数据不能证明稳定内存必然增长 68.2%，但足以否定当前候选在真实大型 DEX 上已经满足生产门槛。

首次启动收益不能替代日常冷启动门禁。标准文件路径命中认证缓存后，在 API 33 样本上启动更快且 PSS 更低；候选资源继续默认关闭、不进入 GUI。下一阶段除启动分段剖析外，还必须记录 100 MB 以上 DEX 的直接缓冲区生命周期、GC 后 PSS、匿名映射与文件映射构成，并扩大同一设备的稳态样本数。未解释 OnePlus 内存波动前，不进入 Alpha 集成版本。

### 大 DEX 分段剖析结论

候选运行时增加仅在内存路径执行的包私有阶段记录器，测试脚本通过系统日志采集阶段耗时，并在启动稳定及发送 `RUNNING_LOW` 内存整理通知后分别保存 `dumpsys meminfo`；设备允许读取 `/proc` 时额外保存 `smaps_rollup`。记录器不参与运行决策、不持久化状态，并由构建期诊断开关控制；正常 Release 构建经 R8 裁剪后不含诊断标记。该插桩只服务内部候选，能力正式开放前必须继续执行产物裁剪审计。

执行 `scripts/build-memory-profile-resources.sh` 可生成内部专用的 `resources-memory-profile.zip`。脚本通过构建期常量保留阶段记录器，随后重新构建并验证正常 `resources.zip` 不含诊断标记；发生中途失败时也会恢复执行前的正常标准、内存和 API 19 资源。使用隐藏的 `--resources` 参数生成同签名剖析 APK 后，通过 `tests/scripts/profile-memory-runtime-apk.sh` 采集数据。脚本不接收证书密码，不负责签名或保存 APK，测试产物不得提交仓库。

同一 329 MB、12 DEX 样本重新完成两台真机各 3 次日常冷启动：

| 设备 | 形态 | 启动中位数 | 稳定 PSS 中位数 | 匿名映射中位数 |
|------|------|--------------|------------------|------------------|
| Classin BH55A / API 33 | 标准文件 | 1587 ms | 169057 KB | 无权限读取 |
| Classin BH55A / API 33 | 内存候选 | 1673 ms（+5.4%） | 170649 KB（+1592 KB） | 无权限读取 |
| OnePlus 5 / API 35 | 标准文件 | 不采信 | 154946 KB | 78656 KB |
| OnePlus 5 / API 35 | 内存候选 | 不采信 | 227945 KB（+72999 KB） | 269592 KB（+190936 KB） |

内存候选的主要阶段中位数如下：

| 阶段 | Classin BH55A / API 33 | OnePlus 5 / API 35 |

| 建立 `InMemoryDexClassLoader` | 56 ms | 791 ms，单轮最高 1765 ms |
| 业务 Application 完成 | 176 ms | 808 ms |

每轮在 Native 返回后 Java 已用堆约 178～181 MB，复制到直接缓冲区后升至约 291～294 MB，增量与 113 MB DEX 总量一致。OnePlus 在业务 Application 完成时 Java 已用堆已回落到约 22～30 MB，证明临时 Java DEX 数组可以回收；长期差异主要来自直接缓冲区和 ART 内存 DEX 的匿名映射，而不是该数组持续泄漏。BH55A 在 Application 完成时尚未回收临时数组，但启动 15 秒后的稳定 PSS 已回落。

发送 `RUNNING_LOW` 不是强制 GC。BH55A 整理前后基本不变；OnePlus 内存候选整理后 PSS 反而增加约 18 MB，说明应用会响应该通知继续分配，不能用该结果证明缓冲区可回收。当前候选对 100 MB 以上 DEX 存在固有常驻内存成本，不能通过简单清空 Java 临时数组消除。

后续优化只保留两个受控方向：先用 JNI 直接缓冲区原型消除 Java 数组到直接缓冲区的第二次复制，降低约一个 DEX 总量的启动峰值；再确认 ART 建立加载器时的匿名映射是否存在可避免副本。前者不能解决长期常驻成本，后者若属于系统实现固有限制，则大型 APK 必须继续使用标准文件路径，内存模式最多作为按 DEX 体积限制的显式候选。

## 停止条件

出现以下任一情况时停止正式接入并保留文件加载默认方案：

- 厂商系统无法稳定维持唯一业务 ClassLoader 或原组件工厂语义。
- 只能通过同进程切换加载器才能恢复启动。
- API 28 以下回退行为相对标准资源出现系统性回归。
- 稳定内存增长或冷启动回退无法通过默认关闭和明确适用范围接受。
- 状态认证、Keystore 异常或覆盖迁移无法形成可预测的失败语义。
