# 工具链轻量化与自动化集成研究

本文规划 Mocika Shield 从桌面手工使用扩展到可重复自动化流水线，并在不牺牲 APK 兼容性的前提下逐步减少外部工具调用。它是工程演进方向，不代表当前已经支持 Gradle 自动加固，也不以“完全摆脱 Java”作为成功标准。

## 目标

- 为脚本和 CI 提供稳定、非交互、可诊断的加固入口。
- 避免 GitHub Actions、Gradle 插件和 GUI 各自复制加固逻辑。
- 优先替换耗时高、行为不稳定或影响原 APK 结构的局部步骤。
- 对尚未覆盖的 APK 结构保留可靠回退，不因追求纯 Rust 降低兼容性。
- 保持 Windows 路径、16 KB 对齐、签名绑定和 Android 4.4 双资源策略不变。

## 演进顺序

### 稳定非交互 CLI 契约

先补齐自动化入口，再开发平台封装：

- 固定命令参数、退出码和机器可读进度/结果格式。
- 配置文件与 GUI 的 `config.toml` 明确区分，不复用应用内部配置。
- 明确输入、输出、覆盖策略、资源模式、环境保护、签名计划和错误分类。
- 不在标准输出混入影响解析的调试信息；敏感数据不得进入日志。
- 同一配置在 Linux、macOS 和 Windows 上产生语义一致的结果。

### GitHub Actions 示例

在 CLI 契约稳定后提供官方工作流示例，负责下载指定版本、校验产物、执行加固并上传构建产物。示例不得内置用户证书，也不把 keystore、密码或业务 APK 上传到项目维护者服务。

首轮只提供可复制的工作流模板，不承诺维护独立在线服务或托管式加固平台。

### Gradle 插件薄封装

Gradle 插件只负责定位 Android 构建产物、组装 CLI 参数、执行 CLI 并把产物接回构建流程。加固、签名、对齐和预检仍由 `shield-core` 与 CLI 负责，插件不得复制协议和 APK 修改逻辑。

在正式实现前必须验证：

- Android Gradle Plugin 不同版本的 Variant API 边界。
- APK 与 AAB 任务的输入输出时机。
- 配置缓存、增量构建和并行任务行为。
- 密钥通过 Gradle 属性、环境变量或外部文件传入时的泄露风险。

### 局部接管 APK 修改链路

按收益和风险由低到高逐项原型：

1. 直接复制未修改 ZIP 条目，保持其压缩方式、顺序和元数据尽可能稳定。
2. 直接替换 DEX、Native 库和少量已知资源条目，并统一执行 4 KB / 16 KB 对齐。
3. 对二进制 `AndroidManifest.xml` 进行受限的定点读写，只覆盖壳接入所需字段。
4. 对已覆盖输入绕过 apktool；遇到未知结构、复杂资源变更或校验失败时明确回退现有链路。

该阶段不直接重写完整 Android 资源表、aapt2 行为或所有历史 APK 变体。是否继续扩大范围由真实性能数据、产物差异和兼容样本决定。

### 签名工具边界

短期继续使用 apksigner 作为 APK 签名与证书解析的权威实现。纯 Rust 签名只有在以下条件同时满足时才进入独立调研：

- Java 启动或分发体积已成为可量化的主要问题。
- 能覆盖 V1、V2、V3、V4 及 lineage 等项目实际需要的签名语义。
- 能与 Android SDK 工具、系统安装器和多版本设备建立一致性测试矩阵。

不能只因“可以生成可安装 APK”就替换成熟签名工具。

## 模块边界

| 模块 | 负责 | 不负责 |
|------|------|--------|
| `shield-core` | APK 检查、修改、对齐、签名计划和稳定错误语义 | CI 平台和 Gradle 生命周期 |
| `apps/shield-cli` | 参数、配置、退出码和机器可读输出 | 复制核心加固实现 |
| GitHub Actions 模板 | 安装 CLI、传递配置、保存产物 | 托管密钥或远程加固 |
| Gradle 插件 | 连接构建 Variant 与 CLI | 解析 DEXB、修改 APK 或实现签名 |
| GUI | 人工任务与本地证书管理 | 充当自动化协议的唯一来源 |

## 验收门槛

- 未修改 ZIP 条目的内容保持一致，必要的元数据变化可解释。
- `extractNativeLibs` 三态、所有 Native 库不压缩策略和 16 KB 对齐继续通过。
- 标准资源与 Android 4.4 资源选择不发生静默变化。
- 加固前证书指纹预检、DEXB 签名绑定和加固后签名链路保持一致。
- ARouter、多 DEX、Android 9、API 19、API 35 16 KB 等现有样本全部复用。
- 新路径失败时给出明确原因；回退行为可观测，不静默产生保护强度不同的产物。
- 记录总体耗时、Java 子进程次数、临时目录体积和产物差异，再决定是否替换下一环节。

## 非目标与停止条件

- 不为宣传“零依赖”一次性重写 ZIP、资源、Manifest 和签名全链路。
- 不让 Gradle 插件成为第二套核心实现。
- 不在自动化模板中保存、上传或打印用户证书密码。
- 若局部原生路径需要长期维护大量厂商、打包器或资源表特例，保留 apktool 回退并停止扩大范围。
- 若性能收益不足以覆盖兼容风险，不替换现有稳定实现。

## 与版本路线的关系

CLI 自动化契约和 GitHub Actions 示例可以作为低风险工程能力独立推进。Gradle 插件必须等待 CLI 契约稳定；AAB 入口必须复用 `1.5.0` 的正式 AAB 设计，不能由插件自行实现。工具链局部原生化属于持续优化，不与 `1.4.0` 内存 DEX 或 `1.5.0` AAB 的正式交付强绑定。
