# 壳类名去品牌化与 JNI 绑定治理

## 目标与实施边界

移除加固输出中的 `dev.mocika.shield.loader.Ld` 原始类名，同时保持 Java 与 Native 的绑定正确。先完成构建期混淆与产物检查，不在本轮引入每次加固随机重写全部类名、运行时生成 DEX 或字符串加密。

本项是独立后续维护批次，不修改已公开的 `1.4.2-rc.3`、不移动标签，也不作为工控用户验证或 `1.4.2` 正式发布的新增阻塞。维护者已批准实施首期，具体交付版本在实现和回归完成后确认；下面未完成的任务不代表已验证。

不增加 GUI 选项、CLI 参数、配置字段或数据库迁移；不改变 DEXB v5、缓存身份、Root 策略、业务 DEX 加载方式、Android 最低版本和 ABI 承诺。旧 APK 必须重新加固才能获得新壳名称，已经安装的旧 APK 不受影响。

## 现状与原因

2026-10-23 检查本机保存的官方 `1.4.1` 标准资源，DEX 类定义中仍存在 `Ldev/mocika/shield/loader/Ld;`，其余壳类为 `msk.*`；ARM64 Native 中也存在对应 JVM 类路径。本次未把该快照当作 rc.3 发布资源的逐字节审计结果。

`Ld` 是 Java 与 Native 的桥接类：

- Java 调用 Native 完成 DEX 注入、解密及运行环境检查。
- `JNI_OnLoad` 使用 `FindClass` 和 `RegisterNatives` 动态绑定方法。
- Native 按类名与方法名回调 `getSignatureSha256(Context)`，读取当前 APK 的签名指纹。

JNI 要求最终名称和方法签名一致，并不要求保留源码包名。`scripts/build-stub.sh`、PowerShell 构建入口及 API 19 资源脚本已有“读取 R8 映射，再重编译 Native”的机制。

当前 `shield-stub/build.gradle.kts` 引入 AGP 默认优化规则。本机缓存的当前 AGP `8.13.2` 在 `proguard-common.txt` 中包含：

```proguard
-keepclasseswithmembernames,includedescriptorclasses class * {
    native <methods>;
}
```

项目另加的 `allowobfuscation` 规则没有消除这条名称保留约束。实施时仍需保存合并后的 R8 配置与映射，确认没有其他生成规则再次锁住名称，不能仅凭源码规则修改就宣称解决。

另有两处必须同步治理：Native 的第四个注册方法 `s(Context, byte[])` 当前写死名称，未经过构建映射；各入口在方法映射解析失败时回退原名，可能掩盖映射缺失或解析错误。

## 方案取舍

| 方案 | 收益 | 成本与结论 |
|---|---|---|
| 只将源码包名换成另一个固定名称 | 可以移除原品牌名称 | 仍保留固定桥接类，且没有治理 JNI 契约；不推荐作为最终方案 |
| 构建期统一混淆并按映射重编译 Native | 沿用现有链路，R8 负责合法 DEX 结构，不必在每次加固时改 ELF | 首期推荐；仍承认固定 `msk` 前缀及其他字符串可被识别 |
| 每次加固重命名壳命名空间并联动改写 DEX、Native、Manifest | 降低不同加固任务之间的名称关联 | 需要额外重写协议、冲突处理和兼容矩阵，收益不等于防脱壳；单独评估，不进入首期 |

名称去品牌化只减少明显静态特征，不改变攻击者控制设备或进程后的安全边界，不承诺无法识别加固、阻止 Hook 或保护已解密的业务代码。

## 首期实现设计

### 壳混淆规则

保留 AGP 默认规则中的其他兼容约束，只针对全局 Native 名称保留块生成受控调整后的构建规则。优先在 `shield-stub` 的 Gradle 构建内处理，输出到构建目录；不修改 SDK、Gradle 缓存或上游 JAR，不在 Bash 与 PowerShell 中各复制一套处理逻辑。

转换必须精确识别预期规则块。规则缺失、重复或上游内容发生未知变化时，构建失败并要求审核，不用宽泛正则删掉所有 `keep`，也不把整份默认配置长期复制进仓库。实施时结合合并后的 R8 配置验证最终约束确实已解除。

对 `Ld` 使用允许混淆但完整保留成员的规则，遵守 JNI 回调类 `{ *; }` 的项目约束。允许改名不等于允许裁剪、内联或改变 Native 回调签名。Application、组件工厂及隔离桥的生命周期与保留边界沿用现有设计。

首期沿用 `msk` 重打包前缀，不把“换成另一个固定前缀”当作额外安全能力。必须检查完整类描述符是否与输入 APK 的全部业务 DEX 冲突；冲突时在生成输出前明确失败，不覆盖业务类，也不现场尝试部分改名。

### 单一 JNI 绑定映射

在现有构建链路中形成一份内部绑定清单，输入为最终 R8 映射和 Stub DEX，记录最终桥接类、注册方法及 Java 回调的名称和 JVM 签名。清单是构建中间产物，不作为新公开接口，也不随加固 APK 分发。Native 同时保留该绑定集合的 SHA-256 摘要供离线核对；摘要不是密钥、不是运行时认证，也不替代实际 JNI 注册验证。

绑定至少覆盖四个 Native 方法 `p`、`q`、`r`、`s` 和 Java 回调 `getSignatureSha256`。方法不能只按短名字匹配：解析须限定到准确的类块与原始签名，避免跨类、重载或行号信息导致误匹配。

- 使用一个平台无关的小型构建工具统一解析和验证，Bash、PowerShell、API 19 入口仅消费结果；不增加独立 crate 或框架。
- 正式最终 Native 编译必须取得完整映射；解析缺失、重复、签名不符均失败，禁止回退猜测原名。映射明确返回原方法名时可以接受，不能把合法的同名映射误判成缺失。
- `s` 也通过编译期常量绑定，并纳入 Cargo 环境变量变更追踪。
- 正式打包拒绝残留原始桥接类名；开发阶段的初始 Native 构建和独立探针可使用隔离的开发默认值，但不能将其误打包为最终资源。
- 现有 API 19 原生探针使用源码中的固定 `Ld`，不能用其通过来代替混淆产物启动验收；需增加消费最终映射的探针或使用完整加固 APK 验证。

### 模块职责

| 位置 | 负责 | 不负责 |
|---|---|---|
| `shield-stub` Gradle 与混淆规则 | 生成受控 R8 规则及合法 Stub DEX | 修改业务 DEX、提供 GUI 配置 |
| 构建绑定工具与现有发布脚本 | 解析绑定、编译 Native、验证同批 DEX 与库、打包资源 | 每次加固时重编译或修改 ELF |
| `shield-core` 现有 DEX 扫描与 Runtime 注入边界 | 在原业务 DEX 加密前核对完整类名冲突，保持输入 APK 不变 | 读取构建源码映射、依赖 GUI 或现场调用 R8 |
| GUI 与 CLI | 沿用现有请求并展示核心错误 | 维护第二套命名规则 |

业务类扫描参考现有 ARouter 扫描能力，但不能直接把其容错跳过当作严格冲突检测：畸形索引、截断和不支持格式必须显式报错，覆盖多 DEX。只抽取最小的类定义读取能力，不为本项重构 DEX 研究子系统或建立通用字节码重写器。

### 标准与工控资源

同一构建先得到 R8 映射及 Stub DEX，再按这份映射重编译标准四 ABI Native。API 19 资源复用同一 DEX、映射和标准库，仅替换 v7a 为 r25c／Rust 1.77.2／API 19 产物；不能再次独立混淆后混用资源。

NDK r29 与 r25c 的现有分工、4.4 v7a／NEON 限制和混合 ABI 排除确认都保持不变。不同平台独立构建不要求混淆结果逐字节相同，但每个发布包内部必须绑定一致、可追溯到同批构建。

## 后续静态标识治理

首期完成后仍会存在 `msk`、Manifest 元数据及其他行为线索，不能把“无原始类名”写成“无品牌特征”。另开批次盘点壳拥有的标识，区分以下情况：

- `dev.mocika.shield.ENV_POLICY`、缓存身份和原组件工厂等字段是核心写入、Java 读取的运行契约，不是普通日志。后续改名必须建立共享名称来源，保持双方一致，审计摘要及缓存认证输入、覆盖安装和旧资源兼容，再决定是否需要独立能力版本。
- `ORIGINAL_APPLICATION`、ARouter 资源、缓存目录和错误码等也可能构成特征，但涉及既有兼容路径，不能为了“消除搜索结果”一次性机械替换。
- 工具内部资源的规范 Native 名、构建源码、映射和诊断档案可以保留可维护名称；最终 APK 的 Native 文件名继续使用既有按任务别名，不重复开发。
- 不改业务 APK 自有的相同字符串或包名。审计必须区分壳自身输出和业务内容，不能扫描整个输出后将业务字符串误判成壳残留并删除。

每任务命名随机化只有在独立方案获批后才进入实现。现有 Native 库别名的等长字符串替换不能直接推广到 DEX 类名：必须验证字符串和类型索引顺序、所有描述符引用、反射名称、Manifest、JNI 路径、ELF 可用槽位及校验；随机名称也须检查全部业务类，不依赖“碰撞概率很低”。不引入运行时联网、系统 Hook、自修改代码或可写可执行内存。

## 验证与失败策略

### 自动化与产物审计

- R8 默认规则转换覆盖正常、缺失、重复及未知内容；JNI 映射覆盖原名合法保留、混淆、重载、类块结束及缺失方法等情况。
- 最终 DEX 中不存在壳自身的原始包路径和 `Ld` 描述符；实际桥接类及所有 JNI 绑定均存在，签名一致。
- 每个正式 ELF 均不含原始 JVM 桥接类路径，且其绑定常量与同包 DEX 一致；字符串扫描只是静态检查，不能替代真实 `JNI_OnLoad` 验证。
- 标准／兼容资源的 DEX 与绑定一致，兼容 v7a API 19 标记及其余 ABI 的标准基线不回归；注入后继续检查 Native 别名、不压缩存储与 16 KB 对齐。
- 构造业务 DEX 与壳类重名、多 DEX、畸形 DEX 和缺映射输入，确认明确失败、无可交付的部分输出，原 APK 字节不变。
- 复用 Stub DEX 指标审计。完整保留 JNI 类可能增加大小，变化须解释后再决定阈值，不自动放宽守门。
- 构建报告保存映射及资源摘要以便定位，不公开用户资料；最终 APK 不携带内部映射。已有签名和加固端到端回归继续通过。

### 运行回归

| 环境 | 验证重点 |
|---|---|
| API 19 v7a／NEON | 最终混淆 DEX 与 r25c 库注册、解密、Dalvik 注入、首次及缓存启动 |
| API 21／23 | 标准 r29 壳和工控 v7a 壳的 ART 注入与向上兼容 |
| Android 9 | 已修复的共享库加载路径与 ARouter，不以新命名重现旧问题 |
| 较新 ARM64 系统 | 同一工控混合 ABI APK 的 64 位启动、签名检查、Root 拒绝策略 |
| 16 KB 系统 | 现有打包和对齐约束、Native 加载及重复启动 |
| x86／x86_64 的 API 21 以上环境 | 对应发布库的真实 JNI 注册及启动；仍不扩张为 4.4 x86 支持 |

同签名覆盖旧壳版本、强停后重启、清除数据后启动、ARouter 首次及缓存路径均须覆盖。缺少环境的项目明确待验证，不能用原生链接成功或未混淆探针通过代替。

发现映射不一致、名称残留、业务类冲突或资源错配，必须在资源发布／输出 APK 交付前失败；不静默恢复旧桥接名称，不跳过安全检查，也不为了启动成功回退到未经验证的资源组合。

## 任务与交付顺序

实施按五步推进：先建立转换与映射契约测试，再调整混淆和 Native 绑定，然后联动全部构建入口及资源审计，随后补齐业务类冲突检测，最后执行完整构建与回归。每一步保留测试结果，全部可用验收完成后整批交付，不拆成碎片 PR。

- [x] 确认类名残留、默认规则、JNI 与三种构建入口，记录方案、边界和后续项。
- [x] 建立绑定解析和规则转换测试，记录默认规则与旧资源保留类名基线。
- [x] 调整 R8 规则，完整保留 JNI 回调类并允许改名，统一四个 Native 方法及签名回调的名称与 JVM 签名。
- [x] 联动 Bash、PowerShell、API 19 构建及最终产物审计，消除正式打包的名称猜测回退；Windows 原生运行另列待验。
- [x] 在现有核心边界增加严格的业务／壳完整类名冲突检测及多 DEX 回归。
- [x] 完成本地标准与工控真实双 DEX 加固、签名、资源审计及完整 macOS `.app`；不把构建通过当作设备启动通过。
- [ ] 完成 Android 设备矩阵和 Windows 原生构建验收。
- [ ] 整阶段提交一个 PR，同步回归与发布说明；维护者确认后安排新的版本，不重打 rc.3。
- [ ] 独立审议 Manifest 等运行契约标识的治理；每任务全命名空间随机化保持后续可选项。

普通文档提交不触发新增重型 CI。绑定解析等轻量测试复用现有检查；完整壳与三平台构建只放在现有手动验证或发布流程，不增加 CLI 发布任务。

回滚以成套构建产物为单位：恢复同一版本的 DEX、映射和全部 ABI Native 后重新构建。不得只回滚某个 `.so` 或只改 Java 名称；已公开版本的修正使用新标签，不覆盖用户已经下载的产物。

## 首期本地实施与验收

2026-10-23，本地已完成首期实现，版本仍沿用工作区 `1.4.2-rc.3`，不是重新发布 rc.3。当前桥接类为 `msk.f`，最终 DEX 中已无 `dev/mocika/shield/loader/`；全部正式 ELF 不含原始桥接路径并使用同一绑定摘要。Manifest 的品牌字段及固定 `msk` 前缀仍保留，后续范围未提前实施。

- 构建：`SHIELD_VERSION=1.4.2-rc.3 make build-stub` 生成标准、API 19 兼容和内部内存候选资源；Bash／PowerShell 的标准自动发现入口仅在契约审计通过后更新，API 19 先审计候选 ZIP 再替换正式资源。打包工具和压缩方法不变。
- JNI：`scripts/stub_bindings.py` 为三个入口统一解析类块、准确签名与行号范围，覆盖 `p/q/r/s` 和签名回调。正式 Native 使用解析后的名称、JVM 签名和绑定摘要；映射缺失不再猜测原名。开发初始 Native 与固定名称探针仍隔离使用默认值。
- 核心：严格类读取作为内部共享能力供冲突检测及 ARouter 扫描使用，支持中文类名和 MUTF-8 代理对；异常索引／长度不静默跳过。冲突按完整类名比较，验证发生在业务 DEX 加密前，原 APK 不变。
- Rust：核心 171 项、CLI 5 项、核心集成 5 项、Native 15 项及 GUI 后端 108 项通过；既有依赖外部条件的忽略项没有改成通过。核心／CLI 严格 Clippy、全仓库 Rust 格式通过。
- 脚本：`python3 -m unittest discover -s scripts/tests -v` 共 32 项通过，覆盖规则转换、映射缺失／歧义、合法行号重复、资源错配、缺库及三个入口的绑定契约。
- Java：按既有回归清单执行 `testDebugUnitTest`，42 项通过。曾误运行 `testReleaseUnitTest`，其未映射的源码测试引用找不到已混淆类；未为该入口放松保留规则，Release 产物另以契约审计和端到端覆盖。
- JNI 本机探针：`python3 tests/scripts/run-stub-jni-host-probe.py` 在 macOS JVM 以 `-Xcheck:jni` 加载生产注册实现，四个方法注册及环境方法调用通过。这不是 Android 解密、签名回调或应用启动验证。
- 无设备端到端：标准混合 ABI、工控混合 ABI 和严格环境策略三组 `run-protect-e2e.sh` 通过，覆盖真实双 DEX、原包不变、签名、旧 ABI 确认排除、业务占位库字节保留、Native 别名及不压缩打包；新增原始桥接包名残留检查。
- 指标：新 Stub 为 30,056 字节、20 类、295 方法、52 字段、480 字符串，`make audit-stub-dex` 在原有上限内通过，未放宽阈值。
- 桌面包：`cargo tauri build --bundles app` 生成 `target/release/bundle/macos/MocikaShield.app`，完整应用 adhoc 签名和严格校验通过；包内标准／API 19 ZIP 再次通过 JNI 契约审计，没有把内部映射作为资源分发。

本机补装 r25c 与 Rust 1.77.2 的 ARMv7 目标，未切换全局 Java 或默认 Rust 版本。SDK 安装器对新下载 r25c 的符号链接解压异常已使用官方压缩包恢复，生产 API 19 Native 已实际重编译，未继续复用旧库。没有连接 Android 设备，也没有可用模拟器镜像；Android 4.4、API 21／23、Android 9、较新 ARM64、16 KB 和 x86 系列的真实启动／缓存／覆盖安装，以及 Windows 原生发布构建仍待验证。
