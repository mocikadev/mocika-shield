# 目录与代码重构结论

这是 2026-07-08 已完成的初次模块拆分记录，不是当前待办。后续共享服务与 Agent 结构以[架构](architecture.md)、[共享应用设计](shared-application.md)和[路线图](../process/roadmap.md)为准。

## 已完成的拆分

| 原问题 | 当前职责 |
|---|---|
| Tauri `main.rs` 集中处理配置、证书、签名、更新与文件操作 | 启动入口只接线；业务适配分别归对应模块 |
| React `App.tsx` 集中所有页面和副作用 | 应用壳、页面、工作流 Hook、共享组件分离 |
| 核心加固编排混合 Manifest、DEX 和运行资源细节 | `protect_api` 编排，`protect/` 各模块维护具体规则 |
| 多入口重复实现业务与资料管理 | `shield-core` 提供 APK 核心，`shield-services` 维护本地用例和状态 |
| Windows Java 子进程启动规则散落 | 复用统一的无控制台启动与路径规范化能力 |

旧计划中的文件行数、建议目录树和分步提交顺序已失效，不再作为重构依据。

## 持续维护原则

- 按职责和变更原因拆分，不按行数机械拆文件，也不为未来功能预建空模块。
- GUI 直接调用共享库；CLI 不依赖 GUI，核心不依赖入口框架，MCP 复用 CLI。
- 一个规则只保留一个实现；路径、证书、密码和协议规则不在各入口复制。
- 先保持现有行为，再独立评审功能变化；新增公共接口、依赖或存储迁移必须说明收益、兼容和回退。
- 完整阶段集中验证和提交，不把逐次调试过程写回长期设计文档。

## 验收

模块调整需覆盖受影响入口、旧命令兼容、Windows 子进程与路径、证书秘密不泄漏及任务快照。构建／静态检查通过不能替代完整应用包或设备业务验证；具体执行范围见[测试清单](../process/test-checklist.md)。
